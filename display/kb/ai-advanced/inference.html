2. PagedAttention 原理

传统 Attention 将 KV Cache 存储在连续内存中，导致严重的内存碎片和浪费：


传统方式 (连续内存):
┌──────────────────────────────────────────────┐
│ [Seq1 KV] [Seq1 KV] [Seq1 KV] [padding...]  │
│ [Seq2 KV] [Seq2 KV] [padding...]            │  ← 内部碎片
│ [Seq3 KV] [padding...................]       │  ← 外部碎片
└──────────────────────────────────────────────┘

PagedAttention (分块管理):
┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐
│ B0 │ │ B1 │ │ B2 │ │ B3 │ │ B4 │  ← 物理块池
└──┬─┘ └──┬─┘ └──┬─┘ └──┬─┘ └────┘
   │      │      │      │
   ▼      ▼      ▼      ▼
  Seq1   Seq1   Seq2   Seq3        ← 逻辑→物理映射表

核心思想：将 KV Cache 划分为固定大小的物理块（Block），通过页表（Block Table）建立逻辑块到物理块的映射，类似操作系统的虚拟内存分页。

优势：

  • 内存浪费仅在最后一个块（平均 0.5 块 = 6% 浪费 vs 传统 60-80%）
  • 支持 Copy-on-Write：共享 prefix 的请求可共享 KV 块
  • 按需分配，无需预分配最大长度

    2. GGUF 量化格式

    GGUF (GGML Unified Format) 是 llama.cpp 使用的模型格式，支持多种量化方案：

    
量化类型对比 (以 Llama-2-7B 为例):

┌──────────┬───────────┬────────┬──────────┬────────────┐
│ 量化类型  │ 文件大小   │ 质量   │ 速度     │ 适用场景    │
├──────────┼───────────┼────────┼──────────┼────────────┤
│ F16      │ ~14 GB    │ 最高   │ 最慢     │ 无损精度    │
│ Q8_0     │ ~7.5 GB   │ 极高   │ 慢       │ 近无损      │
│ Q6_K     │ ~5.5 GB   │ 很高   │ 中       │ 高质量推理  │
│ Q5_K_M   │ ~4.8 GB   │ 高     │ 中       │ 均衡选择    │
│ Q4_K_M   │ ~4.1 GB   │ 良好   │ 快       │ 推荐默认    │
│ Q4_0     │ ~3.8 GB   │ 中等   │ 快       │ 内存受限    │
│ Q3_K_M   │ ~3.3 GB   │ 可接受 │ 很快     │ 极限压缩    │
│ Q2_K     │ ~2.7 GB   │ 较差   │ 最快     │ 实验用      │

└──────────┴───────────┴────────┴──────────┴────────────┘

推荐: Q4_K_M 为性价比最优选择

    2.1 量化原理

    
标准 FP16 权重: [0.123, -0.456, 0.789, -0.012, ...]

Q4_K_M 量化 (4-bit, K-quant, Medium):
┌────────────────────────────────────────────────┐
│ 块大小 = 32 个权重                              │
│ 每块存储:                                      │
│   - 1x FP16 scale (缩放因子)                   │
│   - 1x FP16 min (最小值)                       │
│   - 32x 4-bit 量化值                           │
│                                                │
│ K-quant: 对关键层 (attention) 使用更高精度      │
│          对非关键层 (FFN) 使用更低精度          │
└────────────────────────────────────────────────┘

    推测解码技术 (Speculative Decoding)

    推测解码通过"草稿-验证"模式加速自回归生成，可在不损失质量的前提下实现 2-3x 加速。

    1. 核心原理

    1.1 自回归瓶颈

    
标准自回归解码 (每次只能生成 1 个 token):

Step 1: [prompt] → model → token_1        (200ms)
Step 2: [prompt, t1] → model → token_2    (200ms)
Step 3: [prompt, t1, t2] → model → token_3 (200ms)
...

总延迟 = N × 单步延迟   (受 memory bandwidth 限制)

    核心洞察：生成阶段是 memory-bound 而非 compute-bound。大模型单次前向传播处理 1 个 token 和处理 10 个 token 的时间差距很小（GPU 计算单元未被充分利用）。

    1.2 推测解码思想

    
推测解码 (Draft-Verify 模式):

Draft Phase (小模型, 快速生成候选):
  [prompt] → draft_model → [t1, t2, t3, t4, t5]   (50ms)

Verify Phase (大模型, 并行验证所有候选):
  [prompt, t1, t2, t3, t4, t5] → target_model → ✓✓✓✗?  (210ms)
                                                    ││││
                                                    │││└─ 拒绝, 从此处重新生成
                                                    ││└── 接受
                                                    │└─── 接受
                                                    └──── 接受

结果: 3 个 token 被接受 (比标准多 2 个)
总延迟 ≈ 260ms (vs 标准 3×200=600ms)
加速比 ≈ 2.3x

    1.3 数学保证

    
关键性质: 推测解码的输出分布与目标模型完全一致!

接受概率公式:
  对于 draft token x_i, 接受概率为:
  
  P_accept(x_i) = min(1, p_target(x_i) / p_draft(x_i))
  
  其中:
    p_target(x_i) = 目标模型在位置 i 的概率
    p_draft(x_i)  = 草稿模型在位置 i 的概率
  
  如果拒绝, 从修正分布重新采样:
  p_corrected(x) = max(0, p_target(x) - p_draft(x)) / Z
  Z = Σ max(0, p_target(x) - p_draft(x))

→ 保证输出质量与单独使用目标模型完全相同
→ 不存在精度损失

    2. 实现方式

    2.1 Draft Model 方式

    
┌──────────────────────────────────────────────┐
│              Draft-Verify Pipeline            │
│                                              │
│  ┌──────────┐     ┌──────────────────────┐  │
│  │  Draft   │     │     Target Model     │  │
│  │  Model   │────→│    (大模型)           │  │
│  │ (小模型)  │候选  │                      │  │
│  │ 1-3B     │token │  7B / 70B / 405B    │  │
│  └──────────┘     └──────────┬───────────┘  │
│                              │               │
│                    ┌─────────▼─────────┐     │
│                    │   Token Verifier  │     │
│                    │  (逐位比较接受/拒)  │     │
│                    └───────────────────┘     │
└──────────────────────────────────────────────┘

常见 Draft-Target 配对:
  Llama-2-7B (draft) → Llama-2-70B (target)
  Llama-3-1B (draft) → Llama-3-8B (target)
  DistilBERT (draft) → 同架构大模型

    
# 伪代码: 推测解码核心逻辑
def speculative_decode(draft_model, target_model, prompt, num_speculative=5):
    generated = []
    context = prompt
    
    while not done:
        # Step 1: Draft 模型快速生成 K 个候选
        draft_tokens = []
        draft_probs = []
        x = context
        for _ in range(num_speculative):
            p = draft_model.forward(x)
            t = sample(p)
            draft_tokens.append(t)
            draft_probs.append(p[t])
            x = x + [t]
        
        # Step 2: Target 模型一次前向传播验证所有候选
        # 注意: 这是一次前向传播, 不是 K 次!
        all_input = context + draft_tokens
        target_probs = target_model.forward(all_input)  # [K+1] 个位置的概率
        
        # Step 3: 逐位验证
        accepted = 0
        for i in range(num_speculative):
            p_target = target_probs[i]
            p_draft = draft_probs[i]
            accept_ratio = p_target[draft_tokens[i]] / p_draft[draft_tokens[i]]
            
            if random() < min(1, accept_ratio):
                accepted += 1
                generated.append(draft_tokens[i])
            else:
                # 从修正分布采样
                corrected = normalize(max(0, p_target - p_draft))
                generated.append(sample(corrected))
                break
        else:
            # 所有 K 个都接受, 额外从 target 采样一个
            generated.append(sample(target_probs[-1]))
        
        context = context + generated[-(accepted+1):]
    
    return generated

    3. Medusa

    
Medusa 架构 (多个并行预测头):

                LM Backbone (共享)
                    │
         ┌────┬────┼────┬────┐
         ▼    ▼    ▼    ▼    ▼
       Head0 Head1 Head2 Head3 Head4
       (t+1) (t+2) (t+3) (t+4) (t+5)
         │    │    │    │    │
         ▼    ▼    ▼    ▼    ▼
       Top-K Top-K Top-K Top-K Top-K
       候选   候选  候选  候选  候选
         │    │    │    │    │
         └────┴────┼────┴────┘

            (同时验证所有候选组合)
                   │
                   ▼
            最长接受前缀

    
# Medusa 推理伪代码
def medusa_generate(model, input_ids, num_heads=5, top_k=5):
    """一次前向传播生成多步预测"""
    
    # 获取 backbone hidden states
    hidden = model.backbone(input_ids)
    
    # 所有 Medusa 头并行预测
    candidates = []
    for head_idx in range(num_heads):
        logits = model.medusa_heads[head_idx](hidden[:, -1])
        top_k_tokens = torch.topk(logits, top_k, dim=-1)
        candidates.append(top_k_tokens)
    
    # 构建候选树 (tree attention)
    tree = build_candidate_tree(candidates)  # top_k^num_heads 组合
    
    # 用 tree attention 验证
    # 关键: 使用特殊的 attention mask 使得树中每个节点
    # 只能看到它的祖先节点 (因果性)
    verified = target_model.verify_with_tree_attention(
        input_ids, tree, mask=tree_attention_mask
    )
    
    # 找到最长接受路径
    accepted_tokens = find_longest_accepted_path(verified)
    
    return accepted_tokens

    4. EAGLE

    
EAGLE (Extrapolation Algorithm for Greater Language-model Efficiency):

核心思想: 使用特征级别的自回归外推, 而非 token 级别

┌──────────────────────────────────────────┐
│              EAGLE 架构                   │
│                                          │
│  Target Model Backbone                   │
│         │                                │
│    hidden state h_t                      │
│         │                                │
│  ┌──────▼───────┐                        │
│  │ EAGLE Draft  │                        │
│  │ Head         │                        │
│  │ (1层 MLP)    │  ← 极轻量              │
│  └──────┬───────┘                        │
│         │                                │
│    predicted h_{t+1}                     │
│         │                                │
│  ┌──────▼───────┐                        │
│  │ LM Head      │ → draft token          │
│  └──────────────┘                        │
│                                          │
│  EAGLE 在特征空间做自回归:               │
│  h_{t+1} = f(h_t, embed(token_t))       │
│  比 token 级自回归更容易预测              │
└──────────────────────────────────────────┘

    EAGLE 优势：

  • Draft head 极轻量（1 层 MLP），几乎不影响目标模型推理
  • 特征级外推比 token 级外推准确率更高
  • 可与 Tree Attention 结合（EAGLE-2）
  • 不需要单独的 draft 模型

    6. 性能分析

    
加速比估算:

理想加速比 ≈ K / (1 + c × K/t)

其中:
  K = 推测 token 数
  c = draft 模型相对于 target 的延迟比
  t = target 模型单步延迟比

示例:
  K=5, c=0.05 (draft 比 target 快 20x)
  加速比 ≈ 5 / (1 + 0.05×5) = 5/1.25 = 4x

  K=5, c=0.1 (draft 比 target 快 10x)
  加速比 ≈ 5 / (1 + 0.1×5) = 5/1.5 = 3.3x

实际考虑:
  - Accept rate: 通常 60-80% (与任务相关)
  - 编程/数学任务 accept rate 更高
  - 创意写作任务 accept rate 较低

    批处理与调度策略

    批处理和调度策略是 LLM 推理性能优化的核心，直接影响吞吐量和延迟。

    1. 批处理策略演进

    1.1 Static Batching (传统方式)

    
静态批处理: 等所有请求完成才释放 batch

时间 →
Req1: [===prefill===|=========decode=========|]
Req2: [===prefill===|===decode===|pad|pad|pad|]
Req3: [===prefill===|=====decode=====|pad|pad|]

问题:
  - Req2 先完成但必须等 Req1 (GPU 空闲浪费)
  - padding 导致计算浪费
  - 新请求必须等当前 batch 全部完成

    1.2 Continuous Batching (动态批处理)

    
连续批处理: 每个 step 可以加入/移除请求

时间 →
Step1: [Req1] [Req2] [Req3]           ← 3 个请求
Step2: [Req1] [Req2] [Req3]           ← 继续
Step3: [Req1] [Req2] [Req3] [Req4]    ← Req4 加入
Step4: [Req1] [xxxx] [Req3] [Req4]    ← Req2 完成, 释放
Step5: [xxxx] [xxxx] [Req3] [Req4]    ← Req1 完成, 释放
Step6: [xxxx] [xxxx] [xxxx] [Req4]    ← Req3 完成, 释放

优势:
  - 请求完成即释放, 无等待浪费
  - 新请求可随时加入 batch
  - GPU 利用率显著提升 (2-4x 吞吐提升)

    vLLM 连续批处理实现：

    
# vLLM Scheduler 伪代码
class Scheduler:
    def __init__(self):
        self.running = []    # 正在 decode 的序列
        self.waiting = []    # 等待 prefill 的序列
        self.swapped = []    # 被 swap 到 CPU 的序列
    
    def schedule(self):
        """每步调度逻辑"""
        scheduled = []
        budget = self.max_num_batched_tokens
        
        # 1. 优先处理 running (decode)
        for seq in self.running:
            if budget >= 1:
                scheduled.append(seq)
                budget -= 1
        
        # 2. 有剩余预算则处理 waiting (prefill)
        while self.waiting and budget >= 0:
            seq = self.waiting.pop(0)
            num_tokens = len(seq.prompt_tokens)
            if num_tokens <= budget:
                scheduled.append(seq, is_prefill=True)
                budget -= num_tokens
            elif self.enable_chunked_prefill:
                # 分块 prefill: 只处理部分 token
                scheduled.append(seq, is_prefill=True, chunk=num_tokens)
                budget = 0
        
        # 3. 如果内存不足, swap 低优先级序列到 CPU
        if self.is_memory_critical():
            seq = self.running.pop()
            self.swap_to_cpu(seq)
            self.swapped.append(seq)
        
        return scheduled

    2.2 Priority-Based Scheduling

    
# 基于优先级的调度策略
class PriorityScheduler:
    def __init__(self):
        self.queues = {
            "high": [],    # 付费用户 / 低延迟需求
            "normal": [],  # 普通请求
            "low": [],     # 批处理任务
        }
    
    def add_request(self, request, priority="normal"):
        self.queues[priority].append(request)
    
    def schedule(self, budget):
        """高优先级先调度, 但保证低优先级不饿死"""
        scheduled = []
        
        # 80% 预算给高优先级
        for seq in self.queues["high"]:
            if budget > 0:
                scheduled.append(seq)
                budget -= 1
        
        # 15% 给普通
        for seq in self.queues["normal"]:
            if budget > 0:
                scheduled.append(seq)
                budget -= 1
        
        # 5% 给低优先级 (防止饿死)
        for seq in self.queues["low"]:
            if budget > 0:
                scheduled.append(seq)
                budget -= 1
        
        return scheduled

    3. Prefix Caching

    3.1 基本原理

    
Prefix Caching: 共享相同前缀的请求复用 KV Cache

请求1: [System Prompt (100 tokens)] + [User Q1]
请求2: [System Prompt (100 tokens)] + [User Q2]
请求3: [System Prompt (100 tokens)] + [User Q3]

无 Prefix Caching:
  每个请求都重新计算 100 token 的 system prompt
  → 300 tokens 重复计算

有 Prefix Caching:
  第 1 次: 计算 system prompt → 缓存 KV
  第 2 次: 命中缓存, 直接复用 → 0 tokens 计算
  第 3 次: 命中缓存, 直接复用 → 0 tokens 计算
  → 节省 66% prefill 计算

    3.2 实现架构

    
Prefix Cache 结构:

┌─────────────────────────────────────────┐
│          KV Cache Block Pool            │
│  ┌───┐┌───┐┌───┐┌───┐┌───┐┌───┐       │
│  │B0 ││B1 ││B2 ││B3 ││B4 ││B5 │       │
│  │sys││sys││sys││Q1 ││Q2 ││Q3 │       │
│  │pre││pre││pre│   │   │   │           │
│  └─┬─┘└─┬─┘└─┬─┘└─┬─┘└─┬─┘└─┬─┘       │
│    │    │    │    │    │    │           │
│    └────┼────┘    │    │    │           │
│         │         │    │    │           │
│    [共享前缀]      [独立] [独立] [独立]   │
│    ref_count=3     rc=1  rc=1  rc=1     │
└─────────────────────────────────────────┘

Hash 索引:
  hash("system prompt tokens") → [B0, B1, B2]

    4. Paged KV Cache 管理

    4.1 Block 分配策略

    
class BlockManager:
    def __init__(self, num_blocks, block_size=16):
        self.block_size = block_size
        self.free_blocks = list(range(num_blocks))
        self.block_tables = {}  # seq_id → [block_ids]
    
    def allocate(self, seq_id, num_tokens):
        """按需分配物理块"""
        num_blocks_needed = (num_tokens + self.block_size - 1) // self.block_size
        blocks = []
        for _ in range(num_blocks_needed):
            if self.free_blocks:
                blocks.append(self.free_blocks.pop())
            else:
                # 尝试 swap 或 eviction
                self.evict_low_priority()
                blocks.append(self.free_blocks.pop())
        self.block_tables[seq_id] = blocks
        return blocks
    
    def append_token(self, seq_id):
        """生成新 token 时, 可能需要分配新块"""
        table = self.block_tables[seq_id]
        last_block = table[-1]
        if self.is_block_full(last_block):
            new_block = self.free_blocks.pop()
            table.append(new_block)
    
    def copy_on_write(self, src_seq_id, dst_seq_id):
        """共享 prefix 的 Copy-on-Write"""
        src_blocks = self.block_tables[src_seq_id]
        # dst 共享 src 的块, ref_count++
        self.block_tables[dst_seq_id] = src_blocks.copy()
        for b in src_blocks:
            self.increment_ref(b)

    4.2 驱逐策略

    
KV Cache 驱逐策略 (当显存不足时):

1. LRU (Least Recently Used):
   驱逐最久未使用的块
   → 简单但可能驱逐重要上下文

2. LFU (Least Frequently Used):
   驱逐使用频率最低的块
   → 对热点前缀友好

3. Priority-Based:
   根据请求优先级驱逐低优先级的块
   → 适合有 SLA 的场景

4. Recency + Frequency:
   综合考虑最近使用时间和频率
   → 通常效果最好

    5. FlashAttention 的批处理优化

    
FlashAttention 如何配合批处理:

传统 Attention:
  Q × K^T → [N×N] 矩阵 → Softmax → × V
  需要 O(N²) 显存存储 attention matrix

FlashAttention:
  将 Q, K, V 分块 (tiling)
  在 SRAM 中完成 attention 计算
  不需要存储完整的 N×N 矩阵
  → 显存 O(N), 计算速度更快

FlashAttention + Continuous Batching:
  将多个不同长度的序列 padding 到相同长度
  使用 cu_seqlens 追踪每个序列的真实长度
  避免无效计算

    推理性能基准测试

    系统化的基准测试方法论，覆盖延迟、吞吐量、首 Token 时间等核心指标。

    1. 核心指标定义

    1.1 延迟指标

    
请求延迟分解:

[Request]  [Queuing]  [Prefill]  [Decode × N tokens]  [Response]
   │          │          │              │                  │
   t0         t1         t2             t3                 t4

TTFT (Time To First Token) = t2 - t0
  → 首 token 延迟, 用户体感最敏感
  → 包含排队时间 + prefill 计算时间

TPOT (Time Per Output Token) = (t4 - t2) / N
  → 每个输出 token 的平均时间
  → decode 阶段速度

E2E Latency (端到端延迟) = t4 - t0
  → 请求总延迟

ITL (Inter-Token Latency) = 每个相邻 token 之间的间隔
  → 用户感知的"打字速度"

    1.2 吞吐量指标

    
Throughput (吞吐量) 度量:

1. Request Throughput = 请求数 / 秒
   → 每秒完成多少个请求

2. Token Throughput = token 数 / 秒
   → 每秒生成多少 token (最常用)
   → 区分 input tokens/s 和 output tokens/s

3. Goodput = 满足 SLA 的吞吐量
   → 比如 "TTFT < 500ms 且 TPOT < 50ms" 的有效吞吐

    1.3 指标关系

    
延迟 vs 吞吐量 的权衡:

     延迟 ↑
       │  ×
       │    ×
       │      ×
       │        ×  ×  ×
       │                 ×  ×  × (延迟急剧上升)
       │
       └─────────────────────────→ 吞吐量
       
甜点: 在延迟可接受范围内的最大吞吐量

"""LLM 推理基准测试脚本"""
import asyncio
import time
import statistics
from openai import AsyncOpenAI

async def benchmark(
    base_url: str,
    model: str,
    prompts: list[str],
    max_tokens: int = 256,
    concurrency: int = 50,
):
    client = AsyncOpenAI(base_url=base_url, api_key="none")
    semaphore = asyncio.Semaphore(concurrency)
    
    results = {
        "ttft": [],         # 首 token 延迟
        "tpot": [],         # 每 token 延迟
        "e2e": [],          # 端到端延迟
        "tokens_out": [],   # 输出 token 数
        "errors": 0,
    }
    
    async def run_single(prompt: str):
        async with semaphore:
            start = time.perf_counter()
            first_token_time = None
            token_count = 0
            
            try:
                stream = await client.chat.completions.create(
                    model=model,
                    messages=[{"role": "user", "content": prompt}],
                    max_tokens=max_tokens,
                    temperature=0,
                    stream=True,
                )
                
                async for chunk in stream:
                    if chunk.choices and chunk.choices[0].delta.content:
                        if first_token_time is None:
                            first_token_time = time.perf_counter()
                        token_count += 1
                
                end = time.perf_counter()
                
                if first_token_time:
                    results["ttft"].append(first_token_time - start)
                    results["tpot"].append(
                        (end - first_token_time) / max(token_count - 1, 1)
                    )
                    results["e2e"].append(end - start)
                    results["tokens_out"].append(token_count)
            
            except Exception as e:
                results["errors"] += 1
                print(f"Error: {e}")
    
    # 并发执行
    start_time = time.perf_counter()
    await asyncio.gather(*[run_single(p) for p in prompts])
    total_time = time.perf_counter() - start_time
    
    # 输出结果
    print("=" * 60)
    print(f"模型: {model}")
    print(f"请求数: {len(prompts)} (成功: {len(results['ttft'])}, 失败: {results['errors']})")
    print(f"并发度: {concurrency}")
    print(f"总耗时: {total_time:.2f}s")
    print("-" * 60)
    
    if results["ttft"]:
        print(f"TTFT (首token延迟):")
        print(f"  Mean:   {statistics.mean(results['ttft'])*1000:.1f} ms")
        print(f"  Median: {statistics.median(results['ttft'])*1000:.1f} ms")
        print(f"  P99:    {sorted(results['ttft'])[int(len(results['ttft'])*0.99)]*1000:.1f} ms")
    
    if results["tpot"]:
        print(f"TPOT (每token延迟):")
        print(f"  Mean:   {statistics.mean(results['tpot'])*1000:.1f} ms")
        print(f"  Median: {statistics.median(results['tpot'])*1000:.1f} ms")
    
    if results["e2e"]:
        total_tokens = sum(results["tokens_out"])
        print(f"吞吐量:")
        print(f"  Request: {len(results['e2e'])/total_time:.1f} req/s")
        print(f"  Token:   {total_tokens/total_time:.1f} tokens/s")
    print("=" * 60)

import subprocess
import time

def monitor_gpu(interval=1.0, duration=60):
    """持续监控 GPU 使用情况"""
    results = []
    start = time.time()
    
    while time.time() - start < duration:
        output = subprocess.check_output(
            ["nvidia-smi", "--query-gpu=utilization.gpu,memory.used,temperature.gpu",
             "--format=csv,noheader,nounits"]
        ).decode()
        
        gpu_util, mem_used, temp = output.strip().split(", ")
        results.append({
            "time": time.time() - start,
            "gpu_util": int(gpu_util),
            "mem_used": int(mem_used),
            "temp": int(temp),
        })
        time.sleep(interval)
    
    # 分析
    avg_util = sum(r["gpu_util"] for r in results) / len(results)
    max_mem = max(r["mem_used"] for r in results)
    print(f"平均 GPU 利用率: {avg_util:.1f}%")
    print(f"最大显存使用: {max_mem} MB")
    return results

    6. 常见问题诊断

    
问题: TTFT 过高 (>2s)
├── 原因 1: Prefill 计算慢
│   → 启用 Chunked Prefill
│   → 减小 max_num_batched_tokens
│   → 使用更激进的量化
├── 原因 2: 排队时间长
│   → 增加 max_num_seqs
│   → 增加 GPU 实例
│   → 优化请求路由
└── 原因 3: 长 prompt
    → 启用 Prefix Caching
    → 减少 prompt 长度
    → 使用 prompt compression

问题: TPOT 过高 (>100ms)
├── 原因 1: Batch size 太大
│   → 减小 max_num_seqs
│   → 使用请求优先级调度
├── 原因 2: 显存不足导致 swap
│   → 减小 max_model_len
│   → 使用更激进的量化
│   → 减少 swap_space
└── 原因 3: 通信瓶颈 (多 GPU)
    → 检查 NVLink 拓扑
    → 减小 Tensor Parallel 度
    → 使用 Pipeline Parallel

问题: 吞吐量低
├── 原因 1: Batch 利用率不足
│   → 增加并发请求数
│   → 使用 async HTTP 客户端
├── 原因 2: GPU 利用率低
│   → 增大 max_num_batched_tokens
│   → 检查是否有 CPU 瓶颈
└── 原因 3: 内存碎片
    → 启用 PagedAttention (vLLM)
    → 调整 block size
