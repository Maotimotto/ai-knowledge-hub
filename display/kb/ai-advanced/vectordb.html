Milvus 分布式向量数据库

1. 概述

Milvus 是由 Zilliz 开发的开源分布式向量数据库，专为大规模向量相似性搜索设计。

支持万亿级向量的实时检索，是目前生产环境中应用最广泛的向量数据库之一。

核心特性：

  • 分布式架构，支持水平扩展
  • 多种索引类型（IVF/HNSW/DiskANN 等）
  • 混合查询：向量搜索 + 标量过滤
  • 支持多种距离度量：L2、IP（内积）、Cosine
  • 云原生部署，兼容 Kubernetes

    • 2. 系统架构

    Milvus 2.x 采用存算分离的微服务架构，由以下核心组件组成：

    2.1 接入层（Proxy）

    
Client Request
      │
      ▼
┌──────────────┐
│    Proxy      │  ← 负载均衡、请求路由、结果聚合
│  (无状态)     │
└──────┬───────┘
       │ gRPC
       ▼
┌──────────────┐
│ Coordinator  │
│   Services   │
└──────────────┘

    Proxy 职责：

  • 接收客户端请求（SDK / RESTful API）
  • 请求验证与参数校验
  • 将请求路由到对应 Coordinator
  • 聚合 Worker 返回的中间结果
  • 提供负载均衡能力，可水平扩展

    • 2.2 协调层（Coordinator Services）

    协调层是 Milvus 的"大脑"，包含四类 Coordinator：

    Coordinator 职责
    Root Coordinator DDL 操作（创建/删除 Collection）、Timestamp 分配
    Query Coordinator 查询节点管理、Segment 调度、负载均衡
    Data Coordinator 数据写入管理、Segment 分配、Flush 控制
    Index Coordinator 索引构建调度、索引元数据管理

    2.3 工作层（Worker Nodes）

    Worker 职责
    Query Node 执行向量搜索，加载 Segment 到内存
    Data Node 接收写入数据，写入日志（WAL）
    Index Node 执行索引构建任务

    2.4 存储层

    
┌─────────────────────────────────────────┐
│              存储层                       │
├──────────┬──────────┬───────────────────┤
│  etcd    │  MinIO   │  Pulsar/Kafka     │
│ (元数据) │ (对象存储)│  (消息队列/WAL)    │
└──────────┴──────────┴───────────────────┘
  • etcd：存储元数据、服务发现、分布式锁
  • MinIO/S3：存储 Binlog（段数据）、索引文件
  • Pulsar/Kafka：消息队列，实现写入日志和数据同步

    • 3. 核心索引类型

    3.1 IVF 系列索引

    IVF_FLAT（倒排文件 + 暴力搜索）：

  • 原理：先用 K-Means 聚类将向量分成 nlist 个桶，查询时只搜索最近的 nprobe 个桶
  • 优点：精度可控（nprobe 越大越精确）
  • 缺点：全量数据需加载到内存
  • 适用：百万级数据，需要 100% 可调精度

    • IVF_PQ（倒排文件 + 乘积量化）：

  • 原理：IVF 聚类 + PQ 压缩每个向量
  • 优点：大幅降低内存占用（4-16倍压缩）
  • 缺点：精度损失，需训练
  • 适用：千万到亿级数据，内存受限

    • IVF_SQ8（倒排文件 + 标量量化）：

  • 原理：IVF + 将 float32 量化为 int8
  • 优点：内存减少约 75%，精度损失小
  • 适用：中大规模数据集

    • 3.2 HNSW 索引

    原理： 构建多层跳表图结构，每层是一个近邻图（NSW）。

  • 搜索从最高层开始，逐层下降
  • 每层贪心搜索找到最近邻
  • 时间复杂度：O(log N)

    • 参数调优：

    
index_params = {
    "index_type": "HNSW",
    "metric_type": "L2",
    "params": {
        "M": 16,           # 每个节点的连接数（越大越精确，内存越大）
        "efConstruction": 256  # 构建时的搜索宽度（越大构建越慢，质量越高）
    }
}

    搜索参数：

    
search_params = {
    "metric_type": "L2",
    "params": {
        "ef": 128  # 搜索时的搜索宽度（越大越精确，越慢）
    }
}

    性能特征：

  • M=16, ef=128 时：recall@10 > 99%，延迟亚毫秒
  • 内存占用：约 200 bytes/vector（M=16）
  • 适用：百万到千万级，对延迟要求极高的场景

    • 3.3 DiskANN 索引

    原理： 基于微软的 DiskANN 算法，将图索引存储在 SSD 上。

    特点：

  • 使用 Vamana 图 + PQ 量化
  • 内存中只保留 PQ 量化向量和部分图结构
  • 磁盘上存储完整图和原始向量
  • 适合十亿级数据集，内存有限的场景

    • 参数配置：

    
index_params = {
    "index_type": "DISKANN",
    "metric_type": "L2",
    "params": {
        "build_list": 128,    # 构建时邻居数
        "search_list": 60,    # 搜索时候选列表大小
        "pq_code_budget_gb": 0.125  # PQ 编码内存预算
    }
}

    3.4 索引选型决策树

    
数据量 < 100万？
  ├── 是 → HNSW（延迟优先）或 IVF_FLAT（精度优先）
  └── 否 →
      数据量 < 1亿？
        ├── 是 → 内存充足？HNSW : IVF_PQ
        └── 否 → DiskANN 或 IVF_PQ（分片）

    Pinecone 云原生向量数据库

    1. 概述

    Pinecone 是全球首个全托管的云原生向量数据库，由 Edo Liberty（前 AWS/AI 负责人）创立。

    专注于提供零运维、低延迟、高可用的向量搜索服务。

    核心定位：

  • 完全托管（SaaS），无需运维基础设施
  • Serverless 架构，按使用量付费
  • 毫秒级查询延迟
  • 适合快速上线、不想自建向量数据库的团队

    • 与其他向量 DB 的区别：

    维度 Pinecone Milvus/Qdrant
    部署模式 SaaS 托管 自建/托管
    运维成本 零 中-高
    扩展性 自动 手动配置
    定价 按用量 按资源
    数据控制 云端 完全自主

    2. Serverless 架构模型

    2.1 架构演进

    Pinecone 经历了三个架构阶段：

    
Pod-based → Node-based → Serverless
(2021)       (2023)        (2024)

    Serverless 模型（2024 年推出）：

    
┌─────────────────────────────────────────┐
│            Pinecone Serverless           │
├──────────────┬──────────────────────────┤
│   Compute    │        Storage           │
│  (按查询自动  │  (S3-based, 自动扩展,     │
│   扩缩容)    │   按存储量计费)            │
├──────────────┴──────────────────────────┤
│         冷热数据自动分层管理               │
│   热数据 → 内存缓存（低延迟）              │
│   冷数据 → 对象存储（低成本）              │
└─────────────────────────────────────────┘

    Serverless 优势：

  • 零容量规划：自动扩缩容，无需预估 QPS 和数据量
  • 按量付费：
  • 读取：按查询次数（Read Units）
  • 写入：按写入次数（Write Units）
  • 存储：按向量数据量（GB）
  • 冷启动优化：Pinecone 对冷查询做了优化，首次查询延迟较低
  • 多租户隔离：每个 Index 物理隔离

    • 2.2 Pod-based 模型（传统）

    适合有稳定、可预测工作负载的场景：

    Pod 类型 内存 向量容量 适用场景
    s1 7 GB ~100 万 开发测试
    p1 28 GB ~500 万 生产环境
    p2 56 GB ~1000 万 大规模生产

    3. Namespaces（命名空间）

    Namespaces 是 Pinecone 中的逻辑分区机制，用于数据隔离和多租户。

    3.1 核心概念

    
# 同一个 Index 内，不同 Namespace 的数据完全隔离
index = pinecone.Index("my-index")

# 写入不同 Namespace
index.upsert(vectors=[
    {"id": "vec1", "values": [0.1, 0.2, ...], "metadata": {"source": "doc1"}}
], namespace="tenant-a")

index.upsert(vectors=[
    {"id": "vec1", "values": [0.3, 0.4, ...], "metadata": {"source": "doc2"}}
], namespace="tenant-b")

# 搜索指定 Namespace（只返回该 namespace 的结果）
results = index.query(
    vector=[0.1, 0.2, ...],
    top_k=10,
    namespace="tenant-a"
)

    3.2 使用场景

    场景 说明
    多租户 每个租户一个 namespace，天然数据隔离
    环境隔离 dev/staging/prod 共享一个 Index
    数据版本 不同版本的数据放在不同 namespace
    业务隔离 不同业务线使用独立 namespace

    3.3 性能考量

  • Namespace 越多，查询性能越好（缩小搜索范围）
  • 建议单个 Namespace 不超过 1000 万向量
  • 不同 Namespace 共享相同的 Index 配置（维度、度量等）

    • 4. Metadata Filtering（元数据过滤）

    4.1 Metadata 结构

    
index.upsert(vectors=[
    {
        "id": "doc-001",
        "values": embedding,
        "metadata": {
            "category": "technology",
            "price": 29.99,
            "rating": 4.5,
            "tags": ["AI", "ML", "NLP"],
            "created_at": "2024-01-15",
            "in_stock": True,
            "author": {"name": "John", "org": "OpenAI"}
        }
    }
])

    支持的 Metadata 类型：

  • 字符串（string）
  • 数值（float/int）
  • 布尔（boolean）
  • 字符串列表（list of strings）
  • 嵌套对象（nested object，2024+）

    • 4.2 过滤语法

    Pinecone 使用 JSON 格式的过滤表达式：

    
# 等值过滤
results = index.query(
    vector=query_vector,
    top_k=10,
    filter={"category": {"$eq": "technology"}}
)

# 数值范围
results = index.query(
    vector=query_vector,
    top_k=10,
    filter={
        "price": {"$gte": 10, "$lte": 100},
        "rating": {"$gte": 4.0}
    }
)

# 逻辑组合
results = index.query(
    vector=query_vector,
    top_k=10,
    filter={
        "$and": [
            {"category": {"$in": ["technology", "science"]}},
            {"price": {"$lt": 50}},
            {"tags": {"$in": ["AI", "ML"]}}
        ]
    }
)

# NOT 过滤
results = index.query(
    vector=query_vector,
    top_k=10,
    filter={"category": {"$ne": "sports"}}
)

    支持的操作符：

    操作符 说明 示例
    $eq 等于 {"status": {"$eq": "active"}}
    $ne 不等于 {"status": {"$ne": "deleted"}}
    $gt/$gte 大于/大于等于 {"price": {"$gte": 100}}
    $lt/$lte 小于/小于等于 {"price": {"$lte": 500}}
    $in 在列表中 {"category": {"$in": ["A","B"]}}
    $nin 不在列表中 {"status": {"$nin": ["banned"]}}
    $and 逻辑与 {"$and": [cond1, cond2]}
    $or 逻辑或 {"$or": [cond1, cond2]}

    4.3 过滤性能优化

  • Pre-filter vs Post-filter：Pinecone 采用自适应策略
  • 过滤条件选择性高（过滤掉大部分数据）→ pre-filter（先过滤再搜索）
  • 过滤条件选择性低（保留大部分数据）→ post-filter（先搜索再过滤）
  • 建议：在 metadata 字段上建索引（创建 Index 时指定 metadata_config）
  • 限制：metadata 总大小不超过 40KB/向量

    6.2 完整 RAG 流程示例

    
import openai
from pinecone import Pinecone

pc = Pinecone(api_key="YOUR_API_KEY")
index = pc.Index("knowledge-base")

# 1. 文档索引
def index_document(doc_id, text, metadata):
    embedding = openai.embeddings.create(
        input=text, model="text-embedding-3-small"
    ).data[0].embedding
    index.upsert(vectors=[{
        "id": doc_id,
        "values": embedding,
        "metadata": {**metadata, "text": text[:1000]}
    }])

# 2. 检索
def search(query, top_k=5, filters=None):
    q_embedding = openai.embeddings.create(
        input=query, model="text-embedding-3-small"
    ).data[0].embedding
    return index.query(
        vector=q_embedding,
        top_k=top_k,
        filter=filters,
        include_metadata=True
    )

# 3. RAG 生成
def rag_answer(query):
    context = search(query, top_k=3)
    context_text = "\n\n".join([
        m["metadata"]["text"] for m in context["matches"]
    ])
    response = openai.chat.completions.create(
        model="gpt-4",
        messages=[
            {"role": "system", "content": f"基于以下上下文回答：\n{context_text}"},
            {"role": "user", "content": query}
        ]
    )
    return response.choices[0].message.content

    Qdrant 与 pgvector

    第一部分：Qdrant 向量数据库

    1. 概述

    Qdrant（读作 "quadrant"）是用 Rust 编写的高性能向量数据库，以低延迟和高效过滤著称。

    核心特性：

  • Rust 实现：内存安全、零开销抽象、高性能并发
  • 丰富过滤：向量搜索与标量过滤深度集成
  • 多向量支持：单个 Point 可携带多个命名向量
  • 分布式部署：Raft 共识协议，水平扩展
  • Payload 索引：对过滤字段建立索引，加速过滤

    • 2. 核心架构

    
┌──────────────────────────────────────────┐
│              Qdrant Cluster               │
├──────────────────────────────────────────┤
│  ┌──────────┐  ┌──────────┐  ┌────────┐ │
│  │  Node 1  │  │  Node 2  │  │ Node 3 │ │
│  │ (Leader)  │  │(Follower)│ │(Follow)│ │
│  ├──────────┤  ├──────────┤  ├────────┤ │
│  │ Collection│  │ Shard 2  │  │Shard 3 │ │
│  │ Shard 1   │  │          │  │        │ │
│  └──────────┘  └──────────┘  └────────┘ │
│         Raft Consensus Protocol           │
└──────────────────────────────────────────┘

    存储引擎：

  • 使用自研的 Segment-based 存储
  • 每个 Collection 由多个 Shard 组成
  • 每个 Shard 包含多个 Segment（可变段 + 不可变段）
  • 写入先到可变段（mutable segment），flush 后转为不可变段

    • 3. Rust 优势体现

    特性 影响

    9. 混合 SQL + 向量查询

    这是 pgvector 最大的差异化优势——将向量搜索融入 SQL 查询：

    
-- 基本向量搜索
SELECT id, title, category,
       embedding <=> '[0.1, 0.2, ...]'::vector AS distance
FROM documents
ORDER BY embedding <=> '[0.1, 0.2, ...]'::vector
LIMIT 10;

-- 混合查询：向量搜索 + SQL 过滤
SELECT id, title, category,
       embedding <=> query_vec AS distance
FROM documents
WHERE category = 'technology'
  AND created_at > '2024-01-01'
ORDER BY embedding <=> query_vec
LIMIT 10;

-- 带 CTE 的复杂查询
WITH query_vec AS (
    SELECT '[0.1, 0.2, ...]'::vector AS vec
)
SELECT d.id, d.title,
       d.embedding <=> q.vec AS distance,
       t.avg_rating
FROM documents d
JOIN query_vec q ON true
LEFT JOIN (
    SELECT doc_id, AVG(rating) as avg_rating
    FROM reviews GROUP BY doc_id
) t ON t.doc_id = d.id
WHERE d.category IN ('AI', 'ML')
  AND d.embedding <=> q.vec < 0.5
ORDER BY d.embedding <=> q.vec
LIMIT 20;

-- 聚合 + 向量
SELECT category,
       COUNT(*) as doc_count,
       AVG(embedding <=> '[0.1, ...]'::vector) as avg_distance
FROM documents
GROUP BY category
ORDER BY avg_distance;

-- 全文搜索 + 向量搜索混合
SELECT id, title,
       ts_rank(to_tsvector('english', content), query) AS text_score,
       embedding <=> '[0.1, ...]'::vector AS vec_distance
FROM documents, plainto_tsquery('english', 'vector database') query
WHERE to_tsvector('english', content) @@ query
ORDER BY
    0.3 * ts_rank(to_tsvector('english', content), query) +
    0.7 * (embedding <=> '[0.1, ...]'::vector)
LIMIT 10;

    2. 各数据库深度分析

    2.1 Milvus

    优势：

  • 生产验证最充分，大规模部署案例多
  • 索引类型最丰富（IVF/HNSW/DiskANN 等）
  • 分布式架构成熟，支持万亿级数据
  • 活跃的开源社区，迭代速度快
  • Zilliz Cloud 提供全托管服务

    • 劣势：

  • 组件多（etcd/MinIO/Pulsar），运维复杂
  • 最低资源要求较高
  • 学习曲线较陡

    • 最佳场景：

  • 大规模生产环境（百万到万亿级）
  • 需要多种索引策略
  • 有专职基础设施团队

    • 2.2 Pinecone

    优势：

  • 零运维，开箱即用
  • Serverless 模式自动扩缩容
  • 混合搜索（稀疏+稠密）原生支持
  • 延迟稳定，SLA 保障

    • 劣势：

  • 闭源，数据存储在第三方
  • 成本随规模增长较快
  • 无法自定义索引算法
  • 供应商锁定风险

    • 最佳场景：

  • 快速上线，不想自建基础设施
  • 中小规模（百万到千万级）
  • 对运维成本敏感

    • 2.3 Qdrant

    优势：

  • Rust 实现，性能优异且稳定
  • Payload 过滤能力强，支持复杂条件
  • 多向量支持，适合多模态场景
  • 部署简单（单二进制）
  • 定价合理

    • 劣势：

  • 社区规模小于 Milvus
  • 分布式功能相对 Milvus 较新
  • 大规模（十亿+）案例较少

    • 最佳场景：

  • 需要高性能 + 丰富过滤
  • 多模态/多表示场景
  • 中等规模，注重部署简便性

    • 2.4 pgvector

    优势：

  • 零额外基础设施，复用现有 PG
  • SQL 查询与向量搜索完美融合
  • ACID 事务保证
  • 生态成熟（备份/复制/监控）
  • 学习成本最低（SQL）

    • 劣势：

  • 性能不如专用向量数据库
  • 不支持分布式向量搜索
  • 大规模场景受限（千万级实用上限）
  • 索引类型较少

    • 最佳场景：

  • 已有 PostgreSQL 的团队
  • 需要事务一致性的场景
  • 数据量 < 500 万
  • 快速原型验证

    • 2.5 Weaviate

    优势：

  • 内置向量化模块，无需外部 Embedding 服务
  • GraphQL API 声明式查询
  • 多模态搜索原生支持
  • 内置 RAG 生成模块
  • 模块化架构，可扩展性强

    • 劣势：

  • GraphQL 学习曲线
  • 性能不如 Milvus/Qdrant
  • 模块依赖较多
  • 社区规模中等

    • 最佳场景：

  • 多模态搜索（文本+图像+音频）
  • 需要端到端向量化管道
  • 偏好 GraphQL API

    • 2.6 ChromaDB

    优势：

  • 最简单的 API，几行代码上手
  • 嵌入式部署，无需服务器
  • 内置 Embedding 支持
  • 适合本地开发和实验

    • 劣势：

  • 不支持分布式
  • 性能和规模有限
  • 生产环境稳定性存疑
  • 功能较基础

    • 最佳场景：

  • 本地开发和原型验证
  • 小规模实验（< 10万向量）
  • Jupyter Notebook 中使用

    • 2.7 FAISS

    优势：

  • 性能最高（纯算法库，无网络开销）
  • 索引类型最丰富
  • GPU 加速支持
  • 学术界广泛使用

    • 劣势：

  • 不是数据库（无持久化、无查询语言、无过滤）
  • 需要自行实现数据管理
  • 不支持分布式（需自行分片）
  • C++/Python API

    • 最佳场景：

  • 需要极致性能
  • 作为其他系统的底层引擎
  • 学术研究和实验

from fastapi import FastAPI
from pymilvus import connections, Collection

app = FastAPI()
connections.connect("default", host="milvus", port="19530")
collection = Collection("documents")

@app.post("/search")
async def semantic_search(query: str, top_k: int = 5):
    embedding = get_embedding(query)  # 调用 Embedding 模型
    results = collection.search(
        data=[embedding], anns_field="vector",
        param={"metric_type": "L2", "params": {"ef": 128}},
        limit=top_k, output_fields=["title", "content"]
    )
    return {"results": [hit.to_dict() for hit in results[0]]}
