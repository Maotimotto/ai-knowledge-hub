小而精巧的金融智能体：智能公告解读助手（Regulatory Filing Insight Agent）

一、项目定位

核心概念：一个专注于上市公司公告实时解读的轻量级智能体，帮助中小投资者和专业机构快速理解监管文件的核心价值与风险。

目标用户：

  • 中小投资者（无法负担专业研报服务）
  • 财经记者和自媒体作者
  • 券商营业部客户经理
  • 小型基金公司研究员

    • 市场规模：A股5000+上市公司，每年发布近百万份公告，每份公告平均阅读时间30分钟→自动解读可节省大量时间。

    二、为什么这个项目“小而精巧”且有价值

    痛点分析：

  • 时间成本高：一份年报200-300页，读透需要4-5小时
  • 信息过载：公告中关键信息埋藏在冗长文本中
  • 理解门槛：会计术语、法律条款、监管要求难以解读
  • 实时性差：重大公告发布时，专业解读需要1-2天后才出

    • 解决方案的独特性：

  • 单点突破：只做公告解读，不做全市场分析
  • 实时响应：公告发布后5分钟内生成解读
  • 成本极低：相比人工研究员（年薪30万+），智能体成本可忽略不计
  • 可量化价值：直接节省用户时间，时间=金钱

    • 三、核心功能设计（MVP版本）

    功能1：核心信息提取（RAG+LLM）

    输入：上市公司公告PDF/文本
输出：
- 【一句话总结】用30字概括公告核心内容
- 【关键数字】影响利润/营收/现金流的关键数值
- 【利好/利空标签】自动判断对股价影响方向
- 【同类公告对比】与历史同类公告关键指标对比
- 【风险提示】隐藏的风险点（如商誉减值、诉讼风险）

    功能2：问答式深度挖掘

    用户提问示例：
- “这份股权激励计划的解锁条件苛刻吗？”
- “收购标的的市盈率是多少？合理吗？”
- “这份减持公告中，股东还剩多少股份？”
- “关联交易占公司营收比例多少？”

智能体回答：基于公告原文+行业常识

    功能3：同业对比分析

    当解读业绩预告时：
- 自动拉取同行业3-5家公司的同类数据
- 对比增长率、利润率等关键指标
- 给出“优于/劣于行业平均”的判断

    功能4：时间线串联

    输入：某公司连续发布的多个公告
输出：构建事件时间线，识别：
- 重大事项的进展（如并购从意向到落地）
- 财务数据的变化趋势
- 管理层变动的连锁反应

    四、技术架构（轻量级设计）

    数据层：

    # 只做公告数据，不做全市场数据
数据源：
1. 交易所官方公告API（免费）
2. 巨潮资讯网（合规爬取）
3. 证监会指定信息披露网站

存储：
- 向量数据库：Chroma（轻量，单机部署）
- 关系数据库：SQLite（简化，无需PostgreSQL）
- 缓存：Redis（可选，提升速度）

    处理流程：

    1. 监控新公告发布（每5分钟轮询）
2. PDF解析（PyMuPDF）→ 结构化文本
3. 关键信息提取（预训练NER模型）
4. 向量化存储（BGE-small，轻量模型）
5. 用户查询 → RAG检索 → LLM生成回答

    智能体设计：

    class AnnouncementAgent:
    # 单一职责：只做公告解读
    capabilities = [
        "financial_number_extraction",  # 财务数字提取

        "comparative_analysis",         # 对比分析
        "timeline_construction",        # 时间线构建
    ]
    
    # 不做的事情：
    # - 股价预测
    # - 投资建议
    # - 宏观分析
    # - 技术分析

产出：10分钟完成稿件初稿

    场景3：客户经理服务客户

    客户经理小王：服务100个高净值客户

    七、技术难点与解决方案

    难点1：PDF解析准确率

    问题：公告PDF格式多样，含表格、图片、扫描件
方案：
1. 优先使用交易所结构化数据（如有）
2. 多模态OCR（PaddleOCR+版面分析）
3. 表格结构化识别（Table Transformer）
4. 人工标注1000份样本做微调

    难点2：金融术语理解

    问题：专业术语多（如“计提减值准备”、“递延所得税”）
方案：
1. 构建金融术语知识库（5000+条目）
2. 使用金融预训练模型（如FinBERT中文版）
3. 设计专业提示词模板

    难点3：时效性要求

    问题：公告发布后需5分钟内出解读
方案：
1. 流式处理（非批处理）
2. 预计算行业对比数据
3. 缓存常见公告模板解析
4. 异步处理+WebSocket推送

from abc import ABC, abstractmethod
from typing import Dict, Any, Optional
from pydantic import BaseModel
import logging

logger = logging.getLogger(__name__)

class AgentInput(BaseModel):
    """智能体输入统一格式"""
    user_id: str
    query: str
    context: Dict[str, Any] = {}
    session_id: Optional[str] = None

class AgentOutput(BaseModel):
    """智能体输出统一格式"""
    content: str
    data: Dict[str, Any] = {}
    metadata: Dict[str, Any] = {}
    success: bool = True
    error_message: Optional[str] = None

class BaseAgent(ABC):
    """智能体基类"""
    
    def __init__(self, agent_id: str, config: Dict[str, Any]):
        self.agent_id = agent_id
        self.config = config
        self.name = config.get("name", agent_id)
        self.description = config.get("description", "")
        self.logger = logging.getLogger(f"agent.{agent_id}")
        
        # 初始化模型服务
        self.llm_service = None
        self.init_services()
    
    def init_services(self):
        """初始化服务依赖"""
        from src.engine.model_services.model_manager import ModelManager
        self.model_manager = ModelManager()
        
    @abstractmethod
    async def process(self, input_data: AgentInput) -> AgentOutput:
        """处理输入并返回输出"""
        pass
    
    def validate_input(self, input_data: AgentInput) -> bool:
        """验证输入"""
        if not input_data.query or not input_data.user_id:
            return False
        return True
    
    def log_processing(self, input_data: AgentInput, output: AgentOutput):
        """记录处理日志"""
        self.logger.info(
            f"Agent {self.agent_id} processed query: {input_data.query[:100]}..."

        )

    六、模型管理器设计

    # src/engine/model_services/model_manager.py
import logging
from typing import Dict, Any, Optional
from dataclasses import dataclass
import yaml
import os

logger = logging.getLogger(__name__)

@dataclass
class ModelConfig:
    """模型配置数据类"""
    provider: str
    model_name: str
    api_key_env: Optional[str] = None
    model_path: Optional[str] = None
    temperature: float = 0.1
    max_tokens: int = 1000
    timeout: int = 30

class ModelManager:
    """统一模型管理器"""
    
    def __init__(self):
        self._models: Dict[str, Any] = {}
        self._configs: Dict[str, ModelConfig] = {}
        self.load_configs()
    
    def load_configs(self):
        """加载模型配置"""
        config_path = os.path.join(
            os.path.dirname(__file__), 
            "../../../config/model_configs/llm_configs.yaml"
        )
        
        with open(config_path, 'r', encoding='utf-8') as f:
            config_data = yaml.safe_load(f)
        
        # 解析配置
        for provider, models in config_data.get('models', {}).items():
            for model_name, model_config in models.items():
                config_key = f"{provider}/{model_name}"
                self._configs[config_key] = ModelConfig(
                    provider=provider,
                    model_name=model_name,
                    **model_config
                )
        
        logger.info(f"Loaded {len(self._configs)} model configurations")
    
    def get_model(self, model_key: str) -> Any:
        """获取模型实例（懒加载）"""
        if model_key not in self._models:
            self._models[model_key] = self._load_model(model_key)
        
        return self._models[model_key]
    
    def _load_model(self, model_key: str) -> Any:
        """加载模型"""
        config = self._configs.get(model_key)
        if not config:
            raise ValueError(f"Model {model_key} not found in configuration")
        
        if config.provider == "openai":
            return self._load_openai_model(config)
        elif config.provider == "local":
            return self._load_local_model(config)
        else:
            raise ValueError(f"Unsupported provider: {config.provider}")
    
    def _load_openai_model(self, config: ModelConfig) -> Any:
        """加载OpenAI模型"""
        from langchain_openai import ChatOpenAI
        
        api_key = os.getenv(config.api_key_env) if config.api_key_env else None
        
        return ChatOpenAI(
            model_name=config.model_name,
            temperature=config.temperature,
            max_tokens=config.max_tokens,
            timeout=config.timeout,
            api_key=api_key
        )
    
    def _load_local_model(self, config: ModelConfig) -> Any:
        """加载本地模型（预留）"""
        logger.info(f"Local model loading not implemented yet: {config.model_name}")
        # 返回一个占位符，实际使用时再实现
        return None

    """聊天请求模型"""
    user_id: str
    message: str
    session_id: Optional[str] = None
    context: Optional[Dict[str, Any]] = None

class ChatResponse(BaseModel):
    """聊天响应模型"""
    response: str
    session_id: str
    agent_used: str
    processing_time: float
    sources: List[Dict[str, str]] = []
    risk_warning: str = ""

@router.post("/query", response_model=ChatResponse)
async def chat_query(
    request: ChatRequest,
    logger = Depends(get_request_logger)
):
    """
    处理用户聊天查询
    """
    try:
        # 获取协调器实例
        orchestrator = Orchestrator.get_instance()
        
        # 记录请求
        logger.info(f"Chat request from user {request.user_id}: {request.message[:100]}...")
        
        # 处理请求
        start_time = time.time()
        response = await orchestrator.process_chat(
            user_id=request.user_id,
            query=request.message,
            session_id=request.session_id,
            context=request.context or {}
        )
        processing_time = time.time() - start_time
        
        # 构建响应
        return ChatResponse(
            response=response.content,
            session_id=response.session_id,
            agent_used=response.agent_chain,
            processing_time=processing_time,
            sources=response.sources,
            risk_warning="投资有风险，入市需谨慎。以上分析仅供参考，不构成投资建议。"
        )
        
    except Exception as e:
        logger.error(f"Chat processing error: {str(e)}")
        raise HTTPException(status_code=500, detail="处理请求时发生错误")

  • 初始画像创建：用户注册后，通过引导式问卷或对话，收集风险偏好（保守/稳健/积极）、投资目标（财富保值/增值/特定目标）、投资经验、关注行业等信息。
  • 持仓同步：用户授权后，通过券商API对接或手动/文件导入方式，获取用户真实的持仓组合（标的、成本、数量）。
  • 行为数据沉淀：在用户后续使用中，系统持续记录其交互行为：高频查询的股票、阅读的研报类型、提问的风格（重技术面还是基本面）、对风险提示的反馈等。
  • 画像动态更新：由“用户画像智能体”定期分析用户行为数据，微调其风险偏好标签和兴趣领域，使画像随时间推移越来越精准。
  • 所用技术栈与解决方案：
  • 技术栈：用户行为埋点SDK、问卷系统、券商Open API（如券商与第三方合作的接口）、关系型数据库（存储用户结构化画像）、LLM（用于分析对话历史，提取兴趣点）。
  • 解决方案：设计轻量级、游戏化的问卷降低用户输入门槛。采用差分隐私等技术确保用户持仓数据安全。利用LLM对用户的自由提问进行主题聚类，自动发现其关注点，并更新至画像。

    • 业务流程三：智能问答与决策支持流程 (核心交互)

  • 流程阐述：这是用户最常使用的核心功能，体现了多智能体协作的威力。
  • 意图解析与任务分发：用户输入问题（如“宁德时代今天为什么大跌？对我的持仓影响有多大？”）。“投顾主智能体”（Orchestrator）首先调用“意图理解子智能体”，判断问题类型（个股咨询、持仓归因、宏观解读、概念查询等）。
  • 上下文增强检索：根据问题意图和用户画像（尤其是持仓），组合检索条件。向向量数据库检索相关研报、新闻；向关系/时序数据库查询实时行情、财务数据。
  • 多智能体协同分析与生成：
  • “研究分析子智能体”负责整合检索到的信息，生成对问题本身的客观分析（例如：宁德时代大跌可能与XX电池技术路线新闻、当期财报不及预期有关）。
  • “持仓归因子智能体”被激活，计算该事件对用户具体持仓组合的影响估算（Beta暴露、盈亏金额），并判断是否触及用户的风险阈值。
  • “合规与风险子智能体”对前两者生成的草稿内容进行审核，确保无违规承诺、提示投资风险、注明信息来源。
  • 综合回复与呈现：“投顾主智能体”将各子智能体的输出合成为一份连贯、个性化、合规的最终回复，以对话形式呈现给用户，并可能附上相关的图表、数据来源引用。
  • 所用技术栈与解决方案：
  • 技术栈：LLM（如GPT-4, Claude 3，或微调的金融领域模型）作为各智能体的“大脑”、LangChain/LlamaIndex等智能体框架、RAG检索链条、向量数据库。
  • 解决方案：为不同子智能体设计专属的系统提示词，明确其角色和边界。例如，研究分析智能体的提示词强调“基于事实，区分观点与数据”；合规智能体的提示词是一份严格的审核清单。采用流式输出提升用户体验。

    • 业务流程四：动态持仓追踪与自动化复盘流程

  • 流程阐述：体现系统主动服务价值的关键流程，无需用户触发。
  • 定时触发与数据快照：系统在预设时间（如每周日晚上）自动启动复盘任务。抓取用户持仓的最新行情、周度/月度的关键市场事件和宏观数据。
  • 多维度归因分析：由“持仓归因子智能体”主导，对组合进行深度分析：
  • 收益归因：计算各持仓标的的贡献度，区分行业Beta收益和个股Alpha收益。
  • 风险分析：计算组合波动率、最大回撤，并与用户风险偏好进行对比预警。
  • 事件关联：将期间的重要新闻、研报与持仓标的的表现相关联，解释涨跌原因。
  • 报告生成与个性化摘要：利用“报告生成子智能体”，将上述结构化分析数据，结合自然语言生成技术，自动制作图文并茂的PDF或HTML报告。报告开头生成一段针对该用户的个性化执行摘要，突出其最应关注的点。
  • 推送与交互：通过APP推送、邮件或私信将报告发送给用户。用户可基于报告内容进一步追问（如“为什么A股票这周Alpha收益为负？”），进入业务流程三的智能问答循环。
  • 所用技术栈与解决方案：
  • 技术栈：Celery/Airflow（定时任务）、数据分析库（Pandas, NumPy）、可视化库（Matplotlib, Plotly 或 AntV）、报告生成引擎（Jinja2 + WeasyPrint）、LLM（用于生成摘要和解读文字）。
  • 解决方案：设计模块化、可配置的报告模板。归因分析采用经典的Brinson模型等专业方法。确保报告数据与问答数据同源，保持一致性。

    • 业务流程五：合规风控与审计贯穿流程

  • 流程阐述：该流程非独立存在，而是像“安全带”一样嵌入以上所有流程中。
  • 输入审查：在用户提问进入系统时，先行过滤敏感、违规问题（如“带单”、“稳赚”等）。
  • 过程审查：在智能体生成内容过程中，“合规与风险子智能体”并行工作，审核内容是否存在承诺收益、误导性陈述、来源不明等问题。
  • 输出审查：最终答复发出前，进行最终校验，并自动附加标准化的风险提示语（如“以上信息仅供参考，不构成投资建议”）。
  • 全程留痕：所有用户交互、数据检索记录、智能体的中间思考过程（Chain-of-Thought）均被完整记录，存入审计日志，以满足未来可能的合规审查要求。
  • 所用技术栈与解决方案：
  • 技术栈：规则引擎（用于敏感词过滤）、LLM（作为合规审核员）、日志系统（ELK Stack）、区块链存证服务（可选，用于关键记录防篡改）。
  • 解决方案：建立合规知识库，作为合规智能体的参考。设计红蓝对抗机制，定期用测试用例挑战系统，发现合规漏洞。与法务团队合作，持续更新审查规则和提示词。

    • 业务流程六：系统自优化与迭代流程

  • 流程阐述：让系统在运行中不断学习和进化。
  • 反馈收集：在每次交互后，提供“回答是否 helpful”的简单反馈按钮。定期邀请用户对复盘报告进行评分。
  • 效果评估：分析用户留存率、主动提问频率、反馈正向率等产品指标。评估RAG检索结果的相关性、智能体回答的准确性（可通过专家抽样评审）。
  • 数据飞轮：将高质量的问答对、用户确认过的持仓归因逻辑，作为新的优质数据，经过脱敏和安全处理后，反哺给向量数据库和用于微调LLM，使系统越用越“聪明”。
  • 迭代发布：基于评估结果，迭代优化各智能体的提示词、RAG的检索策略、数据源的质量，并定期发布版本更新。
  • 所用技术栈与解决方案：
  • 技术栈：A/B测试平台、数据分析平台、模型微调框架（如P-Tuning, LoRA）、持续集成/持续部署工具。
  • 解决方案：建立模型性能监控看板。设计谨慎的数据脱敏和隐私保护方案，确保用于训练的数据安全合规。采用渐进式更新策略，避免对用户体验造成突变影响。

    • 总结：业务流程全景图

    用户从注册画像开始，与系统进行智能问答核心交互，同时享受系统自动复盘的主动服务。这一切都建立在强大的数据生态之上，并由合规流程全程护航。系统的表现通过反馈与优化流程形成闭环，驱动自身持续进化。

    最终，用户获得的是一个懂市场、更懂自己、持续学习、安全可靠的AI投顾伙伴体验，完美支撑项目“信息副驾驶”和“决策思维伙伴”的核心定位

    2. 项目定位与核心目标

    2.1 项目定位

    一款以AI智能体为引擎、以对话为交互方式的虚拟投资顾问助手。它不提供直接的投资操作建议，而是通过深度信息整合、个性化解读、持仓归因分析和风险教育，充当用户的“信息副驾驶”和“决策思维伙伴”，帮助用户更高效地理解市场、评估自身持仓，从而做出更理性的独立决策。

    2.2 核心目标

  • 核心功能目标：
  • 即时智能问答：准确回答用户关于市场、行业、持仓个股/基金的各类问题，回答基于最新市场信息与用户个人上下文。
  • 动态持仓追踪与归因：自动监控用户持仓表现，对盈亏进行基本面、行情面、事件面的多维度归因分析。
  • 自动化定期复盘：每周/每月自动生成图文并茂的个性化持仓复盘报告，关联期间重大市场事件。
  • 合规风险内嵌：确保所有交互与产出内容均在监管框架内，主动识别并规避合规风险。
  • 用户体验目标：让用户感觉拥有一个“7x24小时在线、熟悉我所有情况、并能调用海量专业知识的专属投顾”。
  • 商业验证目标：验证“智能体+RAG”架构在复杂金融场景下的实用性与可靠性，为未来更高阶的财富管理服务奠定技术基础。

    • 3. 项目架构

    本项目采用“数据层-引擎层-应用层”的分层架构，核心是多智能体协作系统。

    架构组件说明：

  • 数据层：融合用户私有数据（画像、持仓、行为）、海量外部知识（向量化）和实时行情数据，构成系统的唯一事实源。
  • 智能体协调中枢：接收用户请求或定时任务，调度并管理下述各个智能体的工作流与数据流。
  • 专项智能体：
  • 用户意图识别智能体：利用LLM对用户query进行意图分类与槽位填充，输出结构化任务指令。
  • 专业工具调用智能体：根据任务指令，决策并调用相应的工具（RAG查询、计算、数据获取API）。
  • 复盘报告生成智能体：定时启动，执行复杂的多步查询、分析与排版任务，生成结构化报告。
  • 合规与风控智能体：作为输出前的“守门员”，对内容进行扫描和修正，确保合规。

    5. 核心实现细节（分阶段）

    第一阶段：MVP核心问答 (Weeks 1-8)

  • 基础数据管道：搭建爬虫/API，每日定时获取财经新闻、公告摘要，通过嵌入模型存入向量数据库。
  • 基础RAG链：实现基于用户持仓列表的自动查询改写与检索，返回相关片段。
  • 单一问答智能体：构建一个能调用RAG和简单计算工具（如涨跌幅）的单一智能体，验证端到端流程。
  • 基础前端：实现一个简单的聊天界面，展示回答和引用来源。

    • 第二阶段：多智能体与复盘报告 (Weeks 9-16)

  • 意图识别模块：训练或Prompt工程，使LLM能准确识别用户问题中的意图（如归因、对比、预测、查询）。
  • 工具调用智能体开发：拓展工具集，接入实时行情API、财务指标计算器等。
  • 复盘报告智能体：设计报告模板，开发自动化的数据抓取、分析和Markdown/PDF生成流水线。
  • 多智能体编排：使用LangGraph等框架，将意图识别、工具调用、报告生成等智能体串联成稳定工作流。

    • 第三阶段：系统优化与合规强化 (Weeks 17-24)

  • 合规智能体集成：建立合规关键词库和规则引擎，设计LLM进行最终内容审核与修正的流程。
  • 长上下文优化：针对研报PDF处理，实施高级RAG策略，如父文档分割、摘要索引、混合检索等。
  • 性能与体验优化：实现流式输出、缓存机制，优化检索速度与回答时效性。
  • 用户行为反馈闭环：记录用户对回答的反馈（点赞/点踩），用于后续RAG检索排序和回答质量的优化。

    • 6. 核心输出

  • 交互式聊天界面（Web/移动端H5）：主交互场所，支持文字、语音输入，回答呈现结构化信息（如表格、图表）和引用来源。
  • 个性化定期复盘报告（PDF/Web页面）：
  • 封面摘要：周期表现概览、与大盘对比。
  • 持仓透视：盈亏贡献分析、行业/风格分布。
  • 关键事件回顾：利用RAG提取影响持仓的重大事件及解读。
  • 风险提示与观察建议：基于持仓集中度、波动率等提出观察点。
  • 异动提醒通知（Push/站内信）：当持仓标的出现大幅涨跌、发布重大公告时，触发简要的解读提醒。

    • 7. 主要技术难点与应对策略

    难点描述应对策略
    1. 智能体流程的稳定性复杂多步推理中，LLM可能偏离预期路径或工具调用失败。采用LangGraph等状态机框架严格定义流程；为每个关键步骤设计强大的错误处理与回退机制；实施完善的日志监控。
    2. 长文档处理与精准检索券商研报PDF长达数十页，包含图文表格，直接切片会导致信息丢失。采用层次化切片策略（标题-段落-表格）；为每份研报生成摘要索引；在检索后引入重排序模型提升精度。
    3. 金融数据的准确性与时效性模型生成的内容可能包含“幻觉”或过时信息。RAG作为事实基石，严格限制模型仅基于检索内容生成；所有数据标注来源与时间戳；关键数据（如股价、财务数据）优先从结构化API获取。
    4. 合规风险控制生成内容可能无意中触碰监管红线。设计“预-中-后”三层防线：Prompt工程预设合规立场；合规智能体实时过滤；最终输出附带统一风险提示文本。定期进行人工抽查。
    5. 复杂的用户意图理解用户问题模糊，如“这个怎么样？”需结合上下文理解指代。在意图识别中，显式地将用户持仓列表、最近对话历史作为上下文输入，提升指代消解能力。

    结语：本项目是AI Agent技术在垂直金融领域的一次深度实践。通过构建一个稳定、可靠、合规的“全天候个人投顾助手”，我们不仅能为用户创造巨大价值，更能在金融科技前沿占据有利位置。项目采取分阶段迭代开发，能有效控制风险并持续验证市场反馈。

    三、项目架构详细设计（第一阶段）

    3.1 数据采集层

    3.1.1 数据来源与去重策略

  • 数据源：
  • 巨潮资讯（cninfo.com.cn）：主流免费源，需合规爬虫
  • 上交所/深交所官方API：推荐优先使用，数据结构化好
  • 证监会指定披露网站：备选，更新较慢
  • 去重机制：
  • 根据公告ID（如公告编号+公司代码+发布时间）去重
  • 使用Redis或MySQL存储已处理ID集合
  • 自动化采集：
  • 定时任务（crontab + Python脚本）每5分钟轮询
  • 异步爬虫（aiohttp + asyncio）提高采集效率
  • 数据处理流程：
    •   采集 → 去重 → 下载PDF → 存储至MongoDB（原始文件） → 触发解析任务

    3.1.2 巨潮爬虫合规性说明

  • 仅获取公开披露信息
  • 遵守robots.txt
  • 设置合理请求间隔（>3秒/次）
  • 不进行商业化分发原文，仅用于解读分析

    • 3.2 数据处理层

    3.2.1 PDF解析引擎策略

  • 标准PDF：直接使用PyMuPDF提取文本
  • 扫描件/图片PDF：使用PaddleOCR进行OCR识别
  • 含表格PDF：结合PaddleOCR + 表格识别模型（如Table Transformer）
  • 输出：统一为结构化JSON，包含：
  • 文本段落
  • 表格数据
  • 章节标题
  • 元信息（公司、公告类型、发布时间等）

    • 3.2.2 文本结构化与关键信息提取

  • 公告类型识别：基于规则+关键词匹配，判断属于哪一类公告（如业绩预告、股权变动等）
  • 关键信息提取策略：
  • 规则模板：针对每类公告预定义提取规则（如净利润、变动比例、股东名称等）
  • NER模型：使用HanLP或训练一个小型金融NER模型
  • 关键句定位：基于标题、加粗、段落位置等排版特征
  • 不同文件类型处理策略：
  • 年报/季报：重点在财务数据表
  • 重大合同：重点在金额、期限、违约责任
  • 股权变动：重点在股东名称、比例、价格

    • 3.3 数据存储层协同设计

    存储组件存储内容协同方式
    MongoDB原始PDF文本、解析后的结构化JSON、中间结果作为主文档存储，支持灵活查询和版本管理
    MySQL公司信息、用户信息、公告元数据、关键数值、任务状态结构化数据存储，支持事务和复杂查询
    Milvus公告文本的向量嵌入（BGE-M3生成）用于RAG检索，相似公告查询
    Redis热点公告、用户会话、任务缓存可选，用于提速，非必需

    数据流转示例：

    MongoDB（原始文本） 
→ 解析 → MySQL（结构化关键信息） 
→ 向量化 → Milvus（向量索引）
→ 用户查询 → Milvus检索 → MongoDB召回原文 → 生成答案

    3.4 核心服务层设计

    3.4.1 智能解读引擎（Insight Engine）

  • 架构：RAG（Retrieval-Augmented Generation） + LLM
  • 流程：
  • 用户输入/公告触发
  • 从Milvus检索相似历史公告与知识库条目
  • 拼接Prompt（公告原文+检索结果+指令模板）
  • 调用LLM生成解读
  • 后处理与置信度计算

    • 3.4.2 LLM选择策略

  • 要求：金融知识强、中文理解好、响应快、成本可控
  • 推荐：
  • DeepSeek-V2（优先）：中文能力强，金融语料丰富，API稳定
  • GPT-4/GPT-3.5：备选，效果优但成本较高
  • 本地化模型：ChatGLM3-6B、Qwen-7B（若数据隐私要求高）
  • 提示词设计：
  • 明确角色：你是一名资深证券分析师
  • 结构化输出：总结、关键数字、影响、风险、对比
  • 引用溯源：要求输出时注明来自公告第几页、第几段

    • 3.4.3 结果生成器

  • 输出格式：JSON + 自然语言段落
  • 可溯源设计：
  • 每个关键信息标注来源位置（如：page:3, paragraph:2）
  • 提供“查看原文片段”链接（跳转至MongoDB存储的对应段落）
  • 后处理：
  • 数字单位统一转换
  • 敏感信息过滤
  • 置信度打分（基于LLM输出一致性、规则匹配度）

    • 3.5 应用接口层（Streamlit实现）

    3.5.1 界面模块

  • 公告上传页：拖拽上传PDF，显示解析结果
  • 公告查询页：输入公司代码/公告ID，查看解读
  • 问答对话页：输入问题，获取基于公告的答案
  • 溯源展示页：点击关键信息，高亮显示原文对应位置
