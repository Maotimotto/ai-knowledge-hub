核心概念

MCP（Model Context Protocol）是一个标准的模型上下文协议，为 AI 大模型提供"万能接口"，使其能够与不同的数据源和工具进行无缝交互。类比 USB-C 接口。

MCP 的价值

标准化: 替代碎片化的 Agent 代码集成，建立通用接口规范
即插即用: 通过开源项目建立 AI Agent 生态
跨模型兼容: 一套 MCP Server 可对接不同厂商 LLM

MCP 的两种调用模式

1. Prompt 调用（老办法）

通过自然语言"暗示"让 AI 模仿返回 JSON。问题：易幻觉、无法约束参数类型、换模型失效。

2. 原生 Function Call（现代办法）

通过协议握手输出结构化指令。优势：确定性（只输出JSON）、Schema约束、省Token。

mcp_tool_definition = {
    "name": "translate_service",
    "description": "将中文翻译成英文",
    "parameters": {
        "type": "object",
        "properties": {"text": {"type": "string"}},
        "required": ["text"]
    }
}

MCP 三类传输协议

1. stdio（标准输入输出）

子进程模式，stdin/stdout通信。适用：本地插件。限制：无法跨服务器。

2. SSE（Server-Sent Events）

单向长连接推送。基于HTTP，防火墙友好，内置断线重连。适用：云端AI助手。

3. Streamable-HTTP（流式HTTP）

将响应拆分为JSON块持续发送，支持stateless模式（目前最优）。适用：复杂Agent交互。

维度stdioSSEStreamable-HTTP
物理距离同一台电脑可跨服务器可跨服务器
长连接不需要需要不强制
最佳场景本地插件远程工具调用复杂Agent交互

SSE 代码示例

from flask import Flask, Response
import time

app = Flask(__name__)
@app.route('/mcp/updates')
def mcp_stream():
    def generate():
        for msg in ["正在启动工具...", "分析完毕..."]:
            yield f"data: {msg}\n\n"
            time.sleep(1.5)
    return Response(generate(), mimetype='text/event-stream')

Streamable-HTTP 代码示例

import json, time

def generate_mcp_stream():
    """模拟 MCP Server 流式返回工具调用结果"""
    chunks = [
        {"type": "thought", "content": "正在检索数据库..."},
        {"type": "tool_call", "tool": "search_db", "args": {"id": 101}},
        {"type": "result", "data": "用户等级：金牌会员"}
    ]
    for chunk in chunks:
        yield json.dumps(chunk, ensure_ascii=False) + "\n"
        time.sleep(1)

面试高频问题

Q: Prompt 也能调用，为什么还要 Function Call？ 标准化。Prompt是私有方案，Function Call提供通用接口规范。

核心概念

多MCP协同系统指一个MCP Client同时连接多个MCP Server，将不同业务工具封装为独立MCP服务，通过统一上下文管理器管理会话状态，交由多智能体系统调度。

系统架构

用户输入 → Switch Agent（业务分流）
  ├── Investment Agent ← 投资建议MCP (股价查询/预测/报告)
  ├── Article Check Agent ← 文章风险扫描MCP (规范性/专业性审查)
  ├── Consult Agent ← 金融咨询MCP (本地RAG/网络检索)
  └── Turn Human Agent ← 转人工MCP (场景路由)

关键设计原则

MCP Server独立部署，独立端口
Agent绑定对应MCP Server
Agent间通过handoff（移交策略）实现语义级流转
所有MCP Server会话在同一session中管理

MCP工具并行 vs 串行调用

串行: 分先后调用。如先"规范性审查"再"写审查报告"
并行: 同时调用。如同时调用"规范性审查"和"专业性审查"

MCP SSE 传输层协议 (Server-Sent Events) ⭐⭐进阶

全局定位

SSE 是 MCP 协议的传输层实现之一，提供基于 HTTP 的单向长连接推送，是目前 MCP 远程调用的主流传输方式。

├── 03-MCP的SSE协议 ✅ ← 传输层：SSE
├── 04-MCP的Streamable-HTTP ← 传输层：HTTP（更新）
└── 05-MCP的Prompt调用vs原生Function-Call ← 调用模式

学习价值：SSE 是当前 MCP 远程调用的标准传输方式，防火墙友好、断线自动重连。理解 SSE 的工作原理有助于部署和调试 MCP 服务。

来源：知识星球/AI基础的概念/MCP

核心概念

SSE (Server-Sent Events) 是一种允许服务器主动向客户端发送数据的单向、长连接通信协议。它是 MCP 官方推荐的两种传输方式之一（另一种是本地的标准输入输出 stdio）。

直觉类比

协议类比
传统 HTTP（轮询）没安全感的小孩，每隔一秒问"饭好了吗？"
WebSocket两个人打跨洋电话，你一言我一语，线路搭建复杂
SSE直播间——订阅后，服务器一有新消息就源源不断地推送

为什么 MCP 偏爱 SSE？

轻量级呼吸：AI 调用外部工具往往需要时间，SSE 允许服务器"分批"把进度传回来，不用断开重连
防火墙友好：基于标准 HTTP 协议，绝大多数公司的防火墙不会拦截，部署成本极低
解决"死等"痛点：AI 可以看到工具运行的实时流，大大提升交互体验

实战场景

长时间运行的工具：调用 MCP 工具分析 500 页 PDF 时，服务器不断发送 {"progress": "20%"}，UI 显示进度条
实时数据流检索 (RAG)：每当有新数据，MCP Server 直接推送到上下文，AI 实时更新回答

stdio vs SSE 对比

维度stdio（标准输入输出）SSE（Server-Sent Events）
物理距离工具和 AI 在同一台电脑上工具和 AI 可以在不同的服务器上
复杂度极低（像读写文件）中等（需要 HTTP 环境）
应用场景个人电脑本地插件云端 AI 助手、企业级服务

面试要点

Q：为什么 MCP 不直接用 WebSocket，而要用 SSE？

重点是"单向足够"。AI 调用工具后，主要是等待服务器返回结果。SSE 实现更简单，断线自动重连能力强，且对服务器压力小。

Q：SSE 如果断线了，数据会丢吗？

SSE 协议内置了 Last-Event-ID 机制。客户端重连时会告诉服务器最后收到的消息编号，服务器从该编号之后继续推送。

SSE 标准格式

data: 消息内容\n\n

必须以 data: 开头，以 \n\n 结尾。

总结

本地开发选 stdio，跨服务调用选 SSE。它是 AI 时代的"单行道快线"，让服务器端的变更能像水流一样顺滑地注入到 AI 的感知中。

MCP Streamable-HTTP (流式 HTTP 传输) ⭐⭐进阶

全局定位

Streamable-HTTP 是 MCP 协议的最新传输层标准，将 HTTP 响应拆分为 JSON 块持续发送，支持无状态模式，是 2025 年处理 Agent 长时交互的工业标准。
07-MCP协议
├── 01-MCP协议概述 ← 核心概念
├── 03-MCP的SSE协议 ← 传输层：SSE（传统）
├── 04-MCP的Streamable-HTTP ✅ ← 传输层：HTTP（最新最优）
└── 05-MCP的Prompt调用vs原生Function-Call ← 调用模式

学习价值：Streamable-HTTP 是 MCP 传输层的演进方向，比 SSE 更灵活（支持无状态模式），比 WebSocket 更简单（无需握手升级）。新项目应优先选择 Streamable-HTTP。

来源：知识星球/AI基础的概念/MCP

核心概念

Streamable-HTTP 是一种将 HTTP 响应拆分为多个独立、可解析的 JSON 块 (Chunks) 持续发送给客户端的技术。它是 2025 年处理 Agent 长时对话的工业标准。

直觉类比

传统 HTTP：像去餐馆点餐，厨师必须把"前菜+主食+甜点"全部装进一个大食盒，打包封死才递给你
Streamable-HTTP：像吃回转寿司。厨师每做好一个 JSON 盘子，就顺着传送带转到你面前，你不需要等整顿饭做完

为什么需要 Streamable-HTTP？

告别"响应焦虑"：大模型生成 500 字可能需要 10 秒，通过 Streamable-HTTP，第 0.5 秒客户端就能看到第一个词，体感速度提升 20 倍
结构化数据边传边算：MCP 不仅传输文字，还传输工具调用的参数（JSON），允许客户端在接收到一半 JSON 时就开始预热环境
节省连接资源：比 WebSockets 更省心，本质上还是 HTTP，不需要复杂的握手升级，能轻松穿透各类代理服务器（Nginx, Cloudflare）

实战场景

AI 代码生成器：代码像打字机一样一点点蹦出来，每行生成的代码都能实时通过流式传输进行语法校验
多步骤 Agent 思考链：每完成一个任务，结果就立即"流"给用户，用户能看到 AI 思考的每一步过程

SSE vs Streamable-HTTP 对比

维度SSE (Server-Sent Events)Streamable-HTTP (Chunked JSON)
消息类型纯文本/事件流（适合推送到浏览器）结构化二进制/JSON 块（适合程序解析）
控制力较弱，主要是通知性质强，支持双向控制流的模拟
MCP 语境用于简单的状态更新广播用于复杂的模型推理与工具交互

面试要点

Q：Streamable-HTTP 传输 JSON 时，如果流断了，JSON 解析报错怎么办？

在 MCP 实现中，不传输一个巨大的完整 JSON，而是传输 NDJSON (Newline-Delimited JSON)。每一行都是一个完整的、可独立解析的小 JSON 对象。即使流断了，之前的块也是有效的。

Q：为什么不直接用标准的 HTTP Chunked Encoding？

Streamable-HTTP 实际上就是建立在 Chunked Encoding 之上的应用层协议。它通过特定的"结束标记"和"心跳机制"保证了在不稳定网络下的 AI 交互可靠性。

总结

别让你的 AI 憋大招。无论是为了用户体验，还是为了程序内部的流水线作业，只要涉及到长时交互，请务必启用 Streamable-HTTP。

- Streamable-HTTP = 像回转寿司一样分批传递数据的 HTTP
- 核心价值 = 降低延迟感，支持结构化数据的实时消费
- 工程细节 = 常配合 NDJSON（每行一个 JSON）使用，防止解析崩溃

全局定位

本文档是 MCP 协议层的调用模式选型指南，对比 Prompt 调用和原生 Function Call 两种工具调用方式，帮助开发者做出正确选择。

学习价值：理解 Prompt 调用（语义驱动、易幻觉）vs Function Call（协议驱动、高可靠）的本质区别，是构建稳定 Agent 系统的关键决策。

来源：知识星球/AI基础的概念/MCP

核心概念

Prompt 调用：靠"语言暗示"让 AI 模仿返回格式（手绘的假存折去取钱）
Function Call：靠"协议握手"让 AI 从底层逻辑上输出结构化指令（拿着银行卡去 ATM 机）

这是面试官最喜欢的"原理层"问题，用来区分只会写 Prompt 的调包侠和理解大模型底层逻辑的工程师。

为什么从 Prompt 调用进化到 Function Call？

确定性（JSON 格式控制）：Prompt 调用经常"幻觉"——让它返回 JSON，它偏要在前面加一句"好的，这是你要的 JSON："，导致后端程序崩溃。Function Call 在模型微调阶段就强化了必须只输出 JSON
Schema 约束：Function Call 强制要求参数类型。如果函数需要 int，模型不会给你发 string
节省 Token：Function Call 是经过优化的结构化传输，不需要在 Prompt 里反复唠叨工具的使用说明

使用场景选择

场景推荐方式原因
自动化流水线（如删除数据库条目）Function Call容错率为 0，必须确保参数准确
快速原型开发Prompt 调用不想写复杂的 JSON Schema
逻辑极其简单Prompt 调用如"如果用户骂人，就回复表情包"

面试要点

Q：既然 Prompt 也能实现，为什么 MCP 要专门搞一套 Function Call 协议？

重点在于"标准化"。Prompt 调用是"私有方案"，换个模型可能就失效了。MCP 的 Function Call 提供了一套全行业通用的接口规范，实现了工具的即插即用。

Q：Function Call 一定比 Prompt 准确吗？

不一定。Function Call 的准确度取决于模型的 Tool-use 能力。小型模型（如 7B 以下）在处理复杂的 Function Call 时依然会出错，此时反而需要更强的 Prompt 引导。

MCP 工具定义示例

mcp_tool_definition = {
    "name": "translate_service",
    "description": "将中文翻译成英文的专业工具",
    "parameters": {
        "type": "object",
        "properties": {
            "text": {"type": "string", "description": "待翻译的文本"}
        },
        "required": ["text"]
    }
}

总结

Prompt 是灵魂的沟通，Function Call 是肉体的契约。 在构建工程级 AI 应用（如 MCP Client）时，永远优先选择 Function Call 来确保系统的稳定性，只在需要灵活定义行为模式时使用 Prompt。

- Prompt 调用：基于自然语言的语义理解，易出错，难解析
- Function Call：基于协议的结构化输出，高可靠，易集成
- MCP 的角色：把两种方式都"封装"好了，让你不再纠结底层实现，只需关注业务逻辑
