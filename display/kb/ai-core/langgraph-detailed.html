1. LangGraph 概述

1.1 什么是 LangGraph

LangGraph 是专门用来构建"AI工作流"的工具包，帮你把复杂的AI任务拆成步骤，像搭积木一样组装起来。它是 LangChain 的升级版本，可以有效地处理并行、分支、人工介入等复杂场景。

LangChain 是一个通用的智能体编排工具，工作编排成一系列的节点，用一条工作链把这些节点连接起来，组织成一张有向无环图(DAG)。LangGraph 则支持有环图，适合需要循环、条件判断的复杂工作流。

1.2 为什么需要 LangGraph

LangChain 不方便处理一些复杂工作流：分支、并行、人工介入。LangGraph 解决了以下问题：

  • 复杂任务拆分：比如让AI先查资料再写文章，分步完成
  • 动态调整流程：根据中间结果决定下面的分支路径
  • 分支与并行：一些步骤可以拆分成不同的分支，并行完成后整合结果
  • 多人协作：不同步骤可以用不同模型/API
  • 人工介入：在某些非常关键的位置，必须由人类决定的点，可以人工介入

1.3 核心组件

LangGraph 的基础组件包括：图(Graph)、状态(State)、节点(Node)、边(Edge)、记忆(Memory)。

2. State 核心概念

难度 4/5 核心机制 -- 面试高频考点

2.1 什么是 State

State 是 LangGraph 中的全局共享数据结构（通常是一个 TypedDict 或 Pydantic 模型），它定义了在图(Graph)的各个节点(Node)之间传递、更新和持久化的数据模式。

类比：State 就像是"项目的共享在线文档"。想象你在办一场婚礼：策划师、花艺师、厨师都是"节点"，State 就是那本《婚礼需求手册》。

2.2 为什么需要 State

在传统的 LangChain Chain 中，数据流是线性的(A - B - C)，信息容易丢失。LangGraph 的 State 解决了：

  1. 解决"断片"问题：State 允许数据在循环中反复被修改
  2. 实现"后悔药"（短时记忆）：State 记录了每一步的执行结果，如果 AI 走错了，可以根据历史记录跳回上一步重来
  3. 精准控制：可以决定哪些信息是给 LLM 决策用的，哪些是留给程序自动控制逻辑用的

2.3 与 BufferMemory 的区别

特性BufferMemoryState
存储内容仅聊天记录任意结构化数据(SQL结果、变量、文件路径等)
更新模式追加覆盖或追加（可配置）
适用场景简单对话复杂工作流、多步推理

2.4 State 更新机制

  • 节点通过返回一个字典来更新 State
  • 默认是覆盖模式
  • 使用 operator.add 的 Annotated 注解则是追加模式（常用于消息列表）

设计原则：设计 Graph 的第一步永远不是写 Prompt，而是设计 State 的数据结构。State 设计得好，逻辑判断（Conditional Edges）就像写 if-else 一样自然。

2.5 代码示例：基础 State + 条件循环

import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, END

class AgentState(TypedDict):
    history: Annotated[list[str], operator.add]  # 追加模式
    counter: int  # 覆盖模式

def basic_node(state: AgentState):
    new_counter = state['counter'] + 1
    return {"counter": new_counter, "history": [f"计数更新为 {new_counter}"]}

def decide_to_continue(state: AgentState):
    return "stop" if state['counter'] >= 3 else "continue"

workflow = StateGraph(AgentState)
workflow.add_node("incrementer", basic_node)
workflow.set_entry_point("incrementer")
workflow.add_conditional_edges("incrementer", decide_to_continue, {
    "continue": "incrementer",
    "stop": END
})

app = workflow.compile()
result = app.invoke({"counter": 0, "history": ["任务开始"]})

2.6 Checkpointer（状态持久化）

Checkpointer 是 LangGraph 的持久化层，在每个节点执行完成后自动将 State 序列化并存储。三大核心价值：

  1. 容错与恢复：服务器崩了？重启后读取 State 接着干
  2. 人机协作：某些决策需要人审批，Agent 运行到一半"挂起"等待确认
  3. 时间旅行：回到"三步之前的状态"，修改参数看是否有更好结果
类型适用场景特点
MemorySaver测试/开发程序重启就没了
SqliteSaver生产环境服务器关了数据还在
PostgresSaver大规模生产支持高并发

2.7 Agent Checkpoint 恢复记忆的三个维度

  • 物理跨度 -- 永久：只要数据库没清空，记忆是永久的
  • 逻辑跨度 -- 全量 vs 窗口：设置 max_window_size，只把最近 N 轮对话塞给模型以节省 Token
  • 任务恢复 -- 断点续传：直接从上次中断的步骤开始，无需从头执行

def select_router(state: State) -> Literal[END, "tool_node_a", "tool_node_b"]:

6. 人机协作

在编译图时使用 interrupt_before 或 interrupt_after 参数。当图运行到此处时，Checkpointer 强制保存当前状态并停止运行。等待外部输入后，再通过相同的 thread_id 恢复。

from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import MemorySaver

def ask_sugar(state):
    human_response = interrupt("")  # 中断节点
    state["add_sugar"] = human_response
    return state

# 编译时注入 checkpointer
checkpointer = MemorySaver()
graph = graphBuilder.compile(checkpointer=checkpointer)

# 启动工作流
config = {"configurable": {"thread_id": "some_id"}}
state = graph.invoke(state, config)

# 中断后接收用户输入
userDecision = input("请问您的咖啡需要加糖吗？(是/否):")
# 使用 Command 恢复工作流
result = graph.invoke(Command(resume=userDecision), config=config)

7. 多Agent协作

LangGraph 支持多Agent协作模式，典型架构包括 Supervisor（主管）模式和辩论模式。

7.1 Supervisor 模式

Supervisor 负责路由分发、状态管理、冲突裁决，将任务分配给不同的专业 Agent：

  • General Agent：负责 RAG 业务百科、闲聊
  • SQL Agent：负责 Schema Linking、Text-to-SQL
  • Python Agent：负责复杂计算、数据清洗、生成图表
  • Summarizer Agent：负责多模态结果整合

10. 错误处理

10.1 死循环预防

状态机中设置 Max_Iterations（通常 3 次）。3 次自愈尝试后仍失败，强制中断任务返回中间报错信息，并触发人工干预日志。

10.2 Token 溢出防护

采用窗口滑动与摘要压缩策略：只保留最近 N 轮原始对话，之前的通过 Summarizer Agent 提取核心事实存入 Memory。

10.3 数据库防爆

三层防护：账号只有只读权限、驱动层限制 Max_Rows 和 Timeout、所有 SQL 先过 EXPLAIN 预估成本。

11. 智能体设计模式

构建智能体的两种思路

思路优点缺点
工作流（Workflow）可控性强有一定工作量
Agent通用性强，不需要定制可控性较差

六大设计模式

1. 提示链模式（Prompt Chaining）

对复杂工作分步执行，通过多个前后关联的提示词不断优化，使小参数量模型产生媲美大参数量模型的结果。适用场景：模型能力有限，对结果要求比较高。

2. 分支模式（Branching）

要解决的问题可以从多方面阐述，首先找到最合适的角度，再详细展开。适用场景：可选的多个角度中，有一个特别适合这个问题。

3. 并行模式（Parallel）

解决问题需要的多个中间步骤中，有些步骤互不干扰，可以并行提升速度。适用场景：部分节点互不干扰。

4. 计划-执行模式（Plan-and-Execute）

首先对工作整体进行规划，按照规划的步骤逐步实施。适用场景：工作体量比较大，难以单次完成，但各部分之间有比较紧密的联系。

5. 生成-评估模式（Generate-Evaluate）

生成者负责结果生成，评估者负责评估结果，不合格则指出原因交给生成者继续。适用场景：对结果要求比较高，需要实现自动化。

6. 智能体模式（Agent）

大模型综合使用给出的各种工具，自行决定方案来满足用户需求。适用场景：工作要求比较复杂，无法提出通用的工作流。

12.6 NL2SQL 实现

  1. 对数据库所有表名、字段名进行注释（COMMENT），解释表和字段含义
  2. LangGraph 流程节点中，LLM 调用数据库连接方法读取所有表注释和字段注释作为上下文
  3. 写 SQL 节点中，LLM 调用 NL2SQL MCP 工具，根据上下文完成 SQL 编写并执行

12.7 ChatBI 实战经验

  • Text-to-SQL 幻觉处理：做元数据映射层（Schema Mapper），SQL 执行前用正则抓出表名和字段做白名单比对
  • 多表 Join 优化：将 500 张表按业务线分成主题域，用户提问时先判断业务，只把相关的 10 张表 DDL 喂给模型，准确率从 60% 提到 85%
  • 可视化决策树：数据 < 5 行且是占比 - 饼图；时间序列 - 折线图
  • 指标字典：复杂业务计算公式定义在向量库中，涉及特定指标时先检索计算逻辑作为硬性约束

14. 部署与最佳实践

14.1 面试高频问题

Q: 为什么选 LangGraph 而非其他框架？

LangGraph 能先通过加载数据库节点访问数据库一次，后续节点用上下文反复进行 SQL/Python 编写，避免反复读取。LangGraph 有子图实现（大图嵌套小图），这是其他框架不具备的。

Q: Supervisor 模式 vs Chain 链式架构？

链式架构是静态、线性的，容错性差。Supervisor 模式是动态迭代的，能根据子 Agent 返回结果动态决定下一步，处理并行复杂任务。

Q: 如何做能力扩展？

流程最前端有业务分流节点，可在该节点做意图识别，设置不同路由边策略。根据需求扩展相应边下游的流程支线，无需修改已有节点。

14.2 最佳实践

  1. State 设计优先：设计 Graph 的第一步永远不是写 Prompt，而是设计 State 的数据结构
  2. 信息限流：将大量表按业务线分主题域，查询时只喂相关表的 DDL 给模型
  3. 沙箱安全：Python 代码执行使用 Docker 容器化隔离，跑完就销毁
  4. 窗口滑动：只保留最近 N 轮对话，避免 Token 溢出
  5. 死循环防护：设置 Max_Iterations，超限强制中断
  6. 错误自愈：SQL 写错不报错，而是把正确字段名塞回让模型"反思重写"
