01

知识图谱基础 (Knowledge Graph)

3/5 面试频率 4/5
来源: 知识星球/AI基础的概念 | 前置要求: NLP基础、图论概念

核心概念

知识图谱把碎片化信息连成"实体-关系-实体"的蜘蛛网。如果Embedding是AI的"感性直觉"，知识图谱就是"理性大脑"里的逻辑网。

核心优势

1. 多跳推理

向量检索擅长找"相似"，知识图谱擅长找"关联"。
"周杰伦→妻子→昆凌→母亲→布里斯班"顺藤摸瓜。

2. 消除幻觉

提供确定性事实，图谱写死"北京是中国首都"，AI无法胡说。

3. 可解释性

向量检索是黑盒，知识图谱能清晰展示推理路径。

基本单位：三元组 (Triple)

(Subject, Predicate, Object) — 主体-谓语-客体

(周杰伦, 配偶, 昆凌)
(昆凌, 母亲, 武元庆)
(武元庆, 出生地, 布里斯班)

实战场景

  1. 医疗诊断辅助: 将疾病/症状/药物连成网，推导并发症风险
  2. 金融反欺诈: 发现环形洗钱路径（张三→李四→王五→张三）
  3. GraphRAG增强: 处理长篇文档时提取人物关系，防止信息张冠李戴

代码示例：多跳推理

Python
import networkx as nx

kg = nx.DiGraph()
facts = [
    ("周杰伦", "昆凌", {"relation": "配偶"}),
    ("昆凌", "武元庆", {"relation": "母亲"}),
    ("武元庆", "布里斯班", {"relation": "出生地"}),
]
for s, o, r in facts:
    kg.add_edge(s, o, **r)

def multi_hop_search(graph, start, path):
    current = start
    for rel in path:
        for neighbor, attr in graph[current].items():
            if attr['relation'] == rel:
                current = neighbor; break
    return current

result = multi_hop_search(kg, "周杰伦", ["配偶", "母亲", "出生地"])
# → 布里斯班

知识图谱 vs 向量检索

  • 向量检索：模糊匹配、感性、非结构化语义
  • 知识图谱：精确匹配、理性、结构化事实
  • 最强方案：两者结合 = GraphRAG

面试高频问题

Q: 知识图谱和MySQL区别？ MySQL多层JOIN性能爆炸，图数据库原生支持深度关联快几个数量级。
Q: 有LLM了为何还要建知识图谱？ LLM知识有保质期且易幻觉，知识图谱是外部可信知识源。现在用LLM自动抽取三元组构建。

02

Neo4j 图数据库（详细版）

4/5 面试频率 3/5
来源: 知识星球 | 前置要求: Neo4j基础、数据库原理

核心概念

Neo4j 是一种原生图数据库，数据以"节点（Node）"和"关系（Relationship）"的形式存储，专门处理复杂的关系网。在 GraphRAG 时代，被誉为 AI 的"超级记忆宫殿"。

直觉理解

  • MySQL: 像超大 Excel 表，查"谁是谁的老师"要多次 JOIN
  • Neo4j: 像社交关系地图，顺着线摸过去，绕10圈速度也极快

为什么比 SQL 查关系快

关键词：免索引邻接（Index-free Adjacency）

  • SQL 需要查索引表匹配 ID
  • Neo4j 节点直接存储指向邻居的物理地址指针，是"走"过去的不是"搜"出来的

查询语言：Cypher

用小括号表示点 ()，箭头表示边 -->，语法像画图：

Cypher
// 创建节点
CREATE (a:Hero {name: '亚索', position: '中单'})
CREATE (b:Hero {name: '永恩', position: '上单'})

// 创建关系
CREATE (a)-[:BROTHER_OF]->(b)

// 查询亚索的兄弟
MATCH (a:Hero {name:'亚索'})-[:BROTHER_OF]-(b)
RETURN b.name AS brother
// → 永恩

Python 代码示例

Python
from py2neo import Graph, Node, Relationship

graph = Graph("bolt://localhost:7687", auth=("neo4j", "password"))

# 创建节点和关系
hero1 = Node("Hero", name="亚索")
hero2 = Node("Hero", name="永恩")
rel = Relationship(hero1, "BROTHER_OF", hero2)
graph.create(rel)

# 使用 MERGE 避免重复创建
cypher = """
MERGE (s:Entity {name: 'Apple'})
MERGE (t:Entity {name: 'iPhone'})
MERGE (s)-[r:PRODUCED]->(t)
"""
graph.run(cypher)

批量数据导入

千万级数据不能用 graph.create() 一个个写入：

  • 离线导入: neo4j-admin import 工具
  • 在线分批: Cypher 中 LOAD CSV + PERIODIC COMMIT
  • 幂等操作: 用 MERGE 代替 CREATE，保证"检查存在则跳过"

与其他数据库对比

维度MySQLNeo4j向量数据库
擅长固定结构账单关系错综的知识网模糊语义匹配
关系查询JOIN 性能差原生图遍历极快不擅长
最强方案向量+图 = GraphRAG

06

Neo4j 图数据库（入门）

3/5 面试频率 4/5
来源: 知识星球/AI基础的概念 | 前置要求: 数据库基础、图论概念

核心概念

Neo4j 是一种原生图数据库，它不把数据存在"死板"的表格里，而是以"节点（Node）"和"关系（Relationship）"的形式存储，专门处理复杂的关系网。

直觉类比

  • 传统数据库（SQL）：像一张超大的 Excel 表，找"谁是谁的老师"得查半天表连接（JOIN），查三层关系表就炸了
  • Neo4j：像一张巨大的社交关系地图。每个人是一个点，点与点之间连着线（写着：父子、仇人、暗恋）。顺着线摸过去就行，哪怕绕 10 圈，速度也快得惊人

解决的痛点

  1. 多表联查的噩梦：处理社交网络、风控链路时，SQL 需要大量 JOIN 操作，层级一深内存直接溢出
  2. 语义断层：传统向量检索只知道"猫"和"鱼"语义接近，但不知道"猫吃鱼"这种逻辑。Neo4j 提供逻辑上的确定性

技术对比

对比维度MySQLNeo4jVector DB
擅长领域结构固定的账单关系错综复杂的社交/知识网模糊匹配
关系查询JOIN 性能差原生支持深度关联不支持
核心能力精确事务处理逻辑关系推理语义相似度

目前最强方案：向量数据库 + Neo4j 合体

基本操作示例

Python
from py2neo import Graph, Node, Relationship

# 连接数据库
graph = Graph("bolt://localhost:7687", auth=("neo4j", "password"))

# 创建节点
hero1 = Node("Hero", name="亚索", position="中单")
hero2 = Node("Hero", name="永恩", position="上单")

# 创建关系
rel1 = Relationship(hero1, "BROTHER_OF", hero2)
graph.create(rel1)

# Cypher 查询
query = "MATCH (a:Hero {name:'亚索'})-[:BROTHER_OF]-(b) RETURN b.name AS brother"
result = graph.run(query).data()

Cypher 语言核心语法

Cypher
-- 创建节点
CREATE (n:Person {name: '张三', age: 30})

-- 创建关系
MATCH (a:Person {name: '张三'}), (b:Person {name: '李四'})
CREATE (a)-[:FRIEND]->(b)

-- 查询关系
MATCH (a:Person)-[:FRIEND]->(b:Person) RETURN a.name, b.name

-- 使用 MERGE 避免重复
MERGE (n:Person {name: '张三'}) ON CREATE SET n.created = timestamp()

面试要点

关键词是"免索引邻接 (Index-free Adjacency)"。SQL 需要查索引表来匹配 ID；Neo4j 的节点直接存储了指向邻居的物理地址指针，是"走"过去的，不是"搜"出来的。
Q：什么是 Cypher 语言？
Neo4j 的查询语言。最有特色的是用小括号表示点 ()，箭头表示边 -->。语法就像画图一样。

图数据验证与对齐

4/5 面试频率 3/5
来源: 知识星球 | 前置要求: 图数据库基础、图数据建模

核心概念

图数据验证与对齐是通过约束检查（Schema）、算法比对（Entity Resolution）和采样校验（LLM-as-a-Judge），确保图数据库中的每一个点和每一条线都真实反映了原始信息。

这是 GraphRAG 落地最难的"最后一公里"。

直觉类比

你让机器人帮你整理家谱：

  1. 约束检查：机器人说"张三是他自己的爸爸"，系统直接报错（Schema 报错）
  2. 实体对齐：机器人记了"张三"和"老张"，你得核实是不是同一个人（实体消歧）
  3. 采样校验：你随机抽几页家谱，和原文对照，看看有没有漏掉关键信息

三大验证方法

1. 约束与 Schema 验证（人为控制）

预先定义好"哪些关系是合法的"。如果大模型提取出 (人)-[吃]->(电脑)，而 Schema 定义了"吃"的宾语只能是"食物"，则该条数据被拦截。

2. 实体消歧（Entity Resolution / De-duplication）

最容易出错的地方。利用"模糊匹配 + LLM 二次确认"：

  • 发现两个节点叫"Apple"和"Apple Inc."，计算文本相似度
  • 如果相似度高，发给 LLM 问："在这段上下文里，这两个是一个东西吗？"如果是，合并它们

3. LLM-as-a-Judge（AI 闭环验证）

用一个"更聪明、更贵"的模型去检查"便宜"模型生成的图：

  • 给 GPT-4o 原始文本 + 提取出的三元组
  • 问它："请给这些三元组的准确性打分（1-10），并指出哪些关系是编造的"

实体标准化代码示例

Python
from thefuzz import fuzz

def validate_and_merge_nodes(new_entity_name, existing_entities):
    threshold = 85
    for existing_name in existing_entities:
        score = fuzz.ratio(new_entity_name.lower(), existing_name.lower())
        if score >= 100:
            return f"完全匹配：直接连接到 {existing_name}"
        elif score > threshold:
            return f"疑似重复：'{new_entity_name}' 可能是 '{existing_name}'，建议对齐"
    return "新实体：放心创建"

面试要点

Q：如何衡量知识图谱的质量？
三个指标：准确率（Precision）——提取出来的对不对；召回率（Recall）——有没有漏掉；连通性（Connectivity）——孤立的点多不多
Q：图谱里出现了循环引用怎么办？
利用 Neo4j 的 GDS 插件运行 Cycle Detection 算法，发现异常逻辑后人工介入或程序剔除

总结

"垃圾进，垃圾出 (GIGO)" 是永远的真理。永远不要 100% 相信 LLM 提取的图谱。一个成熟的系统，必须有 40% 的代码在做提取，60% 的代码在做清洗和校验。
03

GraphRAG 技术

4/5 面试频率 4/5
来源: 知识星球 | 前置要求: RAG基础、图数据库基础、LLM应用开发

核心概念

GraphRAG 是一种结合了知识图谱与大语言模型的检索增强技术。它通过将非结构化文本转化为节点（实体）和边（关系）的图结构，实现超越传统向量检索的全局视野和多跳推理。

直觉理解

  • 传统 RAG: 像搜索框，搜"林黛玉"能翻出相关段落，但问"林黛玉的舅妈的婆婆是谁？"就晕了
  • GraphRAG: 先画出巨大的人物关系网，顺着网线一抓，信息跨越几百页也能理清逻辑

解决的核心痛点

  1. 向量检索的"局部短视": Top-K 检索只能找语义相似的"碎片"，无法理解宏观结构
  2. 丢失长程关联: 答案需要跨文档"逻辑拼图"时，传统 RAG 极易断片
  3. 缺乏确定性: 将实体关系固化，LLM 决策建立在确凿的事实之上，降低幻觉

GraphRAG vs 传统 RAG

维度传统 RAGGraphRAG
检索方式语义相似度（Top-K）逻辑路径（多跳遍历）
全局视野弱强（社区摘要）
多跳推理差优
构建成本低高（需 LLM 实体抽取）
适用场景简单问答复杂关系推理

代码示例：图谱检索增强

Python
import networkx as nx

# 1. 模拟 LLM 抽取的实体关系
triples = [
    ("张三", "领导", "李四"),
    ("李四", "负责", "A项目"),
    ("A项目", "获得", "2025年创新奖")
]

G = nx.Graph()
for head, relation, tail in triples:
    G.add_edge(head, tail, label=relation)

# 2. 多跳检索
def graph_rag_query(start_node, depth=2):
    nodes = nx.single_source_shortest_path_length(G, start_node, cutoff=depth)
    context = []
    for node in nodes:
        if node != start_node:
            path = nx.shortest_path(G, start_node, node)
            relation = G[path[0]][path[1]]['label']
            context.append(f"{path[0]} -> {relation} -> {path[1]}")
    return "\n".join(context)

# 查询：张三间接关联了什么奖项？
print(graph_rag_query("张三"))
# → 张三 -> 领导 -> 李四
# → 李四 -> 负责 -> A项目
# → A项目 -> 获得 -> 2025年创新奖

构建成本与优化

  • 成本高: 需要 LLM 进行大量实体抽取，极其耗费 Token
  • 优化策略: 分批抽取 + 聚类归一化，先小模型初筛再 LLM 精抽取
  • 适用判断: 小型简单任务用传统 RAG 性价比更高

面试高频问题

Q: GraphRAG 为什么不全面替代传统 RAG？
成本和时延。构建图谱需 LLM 大量实体抽取，耗费 Token 和时间。小型简单任务用传统 RAG 更划算。
Q: 如何解决图谱中的"同义词"问题？
实体消歧（Entity Resolution）。利用 LLM 推理或聚类算法，将指代同一事物的不同写法合并为同一节点。

图数据建模与验证

3/5 面试频率 3/5
来源: 知识星球 | 前置要求: 图数据库基础、Python基础

核心概念

图数据工程包含两个关键环节：建模（Modeling）— 如何科学地构建图数据，验证（Validation）— 如何确保图谱的准确性。

一、图数据建模

三种段位

青铜：手动 Cypher 脚本

Cypher
// setup.cypher
CREATE CONSTRAINT FOR (u:User) REQUIRE u.id IS UNIQUE;
CREATE (a:User {id: 1, name: '张三'})
CREATE (b:User {id: 2, name: '李四'})
CREATE (a)-[:FOLLOW]->(b);

白金：Python 自动化（最常用）

流程：读取数据 → 提取实体 → 建立连接 → 批量写入

Python
from py2neo import Graph

graph = Graph("bolt://localhost:7687", auth=("neo4j", "password"))
raw_data = [
    {"source": "Apple", "relation": "PRODUCED", "target": "iPhone 15"},
    {"source": "Tim Cook", "relation": "CEO_OF", "target": "Apple"},
]

def build_graph(data):
    tx = graph.begin()
    for item in data:
        cypher = f"""
        MERGE (s:Entity {{name: '{item["source"]}'}})
        MERGE (t:Entity {{name: '{item["target"]}'}})
        MERGE (s)-[r:{item['relation']}]->(t)
        """
        tx.run(cypher)
    graph.commit(tx)

钻石：GraphRAG 自动抽取

利用 GPT-4 等大模型自动从文本分析关系，直接调用 Neo4j 接口生成图谱。

关键原则

  • 数据即代码: 所有 Schema 约束、索引创建必须保留在 Git 仓库的脚本中
  • 幂等操作: 用 MERGE 代替 CREATE，避免重复创建
  • 版本控制: 业务逻辑变化时代码能记录演变历史

二、图数据验证：三级质检体系

1. Schema 约束检查

预先定义合法的关系类型。如果 LLM 提取出 (人)-[吃]->(电脑)，而 Schema 定义"吃"的宾语只能是"食物"，则拦截该条数据。

2. 实体消歧（Entity Resolution）

Python
from thefuzz import fuzz

def validate_and_merge(new_entity, existing_entities, threshold=85):
    for existing in existing_entities:
        score = fuzz.ratio(new_entity.lower(), existing.lower())
        if score >= 100:
            return f"完全匹配：连接到 {existing}"
        elif score > threshold:
            return f"疑似重复：'{new_entity}' 可能是 '{existing}'"
    return "新实体：放心创建"

# 测试
existing = ["Apple Inc.", "Microsoft", "Elon Musk"]
for e in ["apple", "ElonMusk", "OpenAI"]:
    print(f"{e} → {validate_and_merge(e, existing)}")
# apple → 疑似重复
# ElonMusk → 疑似重复
# OpenAI → 新实体：放心创建

3. LLM-as-a-Judge

用更强大的模型检查便宜模型生成的图谱：给 GPT-4o 原文 + 三元组，让它打分（1-10）并指出哪些关系是编造的。

质量衡量指标

指标含义
准确率 Precision提取出来的对不对
召回率 Recall有没有漏掉关键信息
连通性 Connectivity孤立节点多不多

面试高频问题

Q: 如何往 Neo4j 导入千万级数据？
用 neo4j-admin import（离线）或 LOAD CSV + PERIODIC COMMIT（分批提交），绝对不能一个个 graph.create()。
Q: 如何衡量知识图谱的质量？
三个指标：准确率（提取的对不对）、召回率（有没有遗漏）、连通性（孤立点多不多）。
05

LLM-based NER 实体关系联合抽取

4/5 面试频率 4/5
来源: 知识星球 | 前置要求: NLP基础、知识图谱概念、Prompt设计

核心概念

在 GraphRAG 时代，NER（命名实体识别）从简单的"标注工具"进化为"图谱建筑师"。通过精心设计的 Prompt，让大模型在阅读文本时同时识别实体和关系，并直接输出为图数据库可读的格式。

传统 NER vs GraphRAG 中的 NER

  • 传统 NER: 像"扫描仪"，只告诉你哪几个字是人名
  • GraphRAG 的 NER: 像"高级调查员"，一边看文章一边画线，不仅识别"马斯克"是人，还连好"马斯克→[创立]→特斯拉"

NER 在 GraphRAG 中的三个核心子任务

1. 节点识别（The Node Picker）

从杂乱文档中挑出重要实体（论文的"算法名称"、财报的"关键财务指标"）

2. 动态消歧（The Identity Fixer）

结合上下文判断不同页面的"老王"和"王局长"是否为同一人，是则合并

3. 摘要总结（The Property Summarizer）

将文本中关于某实体的所有描述总结为精简属性，存入节点属性

实战示例

输入: "长期服用阿司匹林可能导致胃黏膜损伤，建议配合奥美拉唑使用。"

LLM 抽取结果:

  • 实体: 阿司匹林[药物]、胃黏膜损伤[副作用]、奥美拉唑[药物]
  • 关系: (阿司匹林)-[导致]->(胃黏膜损伤)、(奥美拉唑)-[缓解]->(胃黏膜损伤)

prompt_template = """

输出格式要求为 JSON 列表：
[
  {"subject": "实体1", "subject_type": "类型",

]

【文本】：
2024年，OpenAI 发布的 Sora 模型在全球引发轰动，山姆·奥特曼表示这将改变电影行业。
"""

Token 消耗优化

  1. 分批抽取: 将长文档切块，逐块抽取
  2. 聚类归一化: 先小模型做初步 NER 过滤，再用 LLM 对关键段落做关系补全
  3. 缓存机制: 已识别的实体不再重复抽取

面试高频问题

Q: 有 LLM 了为什么不直接喂所有文本，还要费劲建图？
1. LLM 长文本会遗忘细节；2. 多跳推理(A→B→C)时 LLM 容易出错，图数据库是专家；3. 图谱提供稳固知识骨架，LLM 负责语言润色，两者结合降低幻觉。
Q: NER 在大模型时代死了吗？
没死，只是从"主角"变成了"大脑的一部分"。现在的 NER 不纠结于单字标注，而是通过 Prompt 引导 LLM 产生高质量结构化知识块。
