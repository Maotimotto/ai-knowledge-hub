RAG介绍
大模型的局限性

LLM 虽然强大，但是也存在一些很难根除的“疾病”：

+ - * 1. 知识时效性

LLM 因其具有海量参数，需要花费相当的物力与时间成本进行预训练和微调，同时商用 LLM 还需要进行各种安全测试与风险评估等。因此 LLM 会存在一定的知识滞后问题，无法回答训练时间点之后相关的问题。

+ - * 1. 领域知识缺失

LLM 掌握了大量通用知识。但是在一些细分小众专业领域，可能存在很少或者完全没有训练数据。因此 LLM 无法掌握或完全不了解该领域相关的知识，也就无法准确回答这些领域相关的问题。

+ - * 1. 无法确定信息来源

LLM 在生成回答时，无法确定其回答内容的依据，也就无法确定其回答的可靠性。

+ - * 1. 幻觉

LLM 在生成回答时，可能会一本正经的胡说八道，这被称为 LLM 的“幻觉”问题。“幻觉”可以体现为错误陈述或编造事实、错误的复杂推理或者在复杂语境下理解能力不足等。

“幻觉”产生的原因可能是训练知识存在偏差，这些信息被 LLM 学习后在输出中复现；或者是 LLM 训练时过度泛化，将普通的模式应用在特定场合导致不准确输出；也可能是 LLM 本身没有真正学习到训练数据中深层次的含义，导致在一些需要深入理解或复杂推理的任务中出错；还有可能是 LLM 缺乏某些领域的相关知识，在面临这些领域的相关问题时编造不存在的信息。

因此，LLM 的强大并不能掩盖其当前仍存在的缺陷，但也正是这些不足促发着人工智能不断发展，比如研发更先进的模型架构、训练技术；使用更高效的数据清晰与预处理方法获取更高质量的训练数据；使用更先进的方法提升模型输出的可解释性等。

1. RAG 简介

为了改善 LLM 在时效性、可靠性与准确性方面的不足，以便让其能够在更多场景下发挥作用，各种针对 LLM 优化的方法应运而生。RAG（Retrieval-Augmented Generation，检索增强生成）就是其中一种被广泛研究和应用的优化架构。

RAG的基本思想为：将传统的生成式 LLM 和实时信息检索技术相结合，为 LLM 补充来自外部的相关数据和上下文，来帮助 LLM 生成更加准确可靠的内容。这使得 LLM 在生成内容时可以依赖实时与个性化的数据和知识，而非仅仅依赖训练知识。

借助RAG，LLM 能够在生成时利用更广泛、更深入、更新、更准确的外部知识；并且能够更高效地利用计算资源在短期内提升 LLM 输出能力，避免直接扩展 LLM 参数或以更高的成本和更长的时间去训练 LLM。RAG就相当于在 LLM 回答时给它一本参考书。

通常情况下，可以将一个RAG应用分为数据索引（Indexing）和数据查询（Query）两个阶段：

+ 1. 数据索引阶段

RAG的核心之一是通过检索来增强生成，那么首先就需要准备可以检索的内容。传统计算机检索技术通常使用的是关键词检索，通过关键词的匹配程度来对知识库中的信息进行精确或模糊的检索，计算相关性并排序输出。但是在RAG应用中，最常见的检索方式是使用向量的语义检索来获取相关数据块，因此向量存储索引是RAG应用中最常见的索引形式。

数据索引阶段通常包含以下几个关键阶段：

加载（Loading）：RAG应用需要的知识数据可能以不同形式不同格式存在，可能是结构化、半结构化、非结构化的数据，可能是PDF、HTML、Word或Markdown等格式，需要对这些数据统一进行处理和解析，将其转换为能够读取和使用的数据。

分割（Splitting）：为了能够更精确地检索到相关数据，需要将一个较大的内容分割成一个个小的知识块。

嵌入（Embedding）：分割成一个个知识块之后，需要对知识块进行嵌入，将知识块转换为向量。

索引（Indexing）：将向量化之后的知识块存储到向量数据库中。向量数据库会提供强大的向量检索算法与管理接口，后续可以方便地对输入问题进行语义检索。不过索引形式也并非只有向量数据库索引这一种，很多应用也会根据自身需要来构造其他形式的索引，如知识图谱索引、关键词表索引等。

+ 1. 数据查询阶段

在数据索引准备完毕之后，RAG应用需要在数据查询时检索数据并协助生成。

检索（Retrieval）：检索是借助数据索引从存储库中查找出相关的知识块，并按照相关性进行排序。经过排序的知识块将作为参考上下文用于协助后续的生成。

生成（Generation）：将检索阶段输出的相关知识块与用户原始的查询问题构造为 Prompt，输入给 LLM，LLM 根据 Prompt 生成内容。

随着RAG不断演进与优化，一些新的处理阶段被纳入流程，典型的两个阶段为检索前处理和检索后处理：

检索前处理（Pre-Retrieval）：检索前处理通常用于完成如查询转换、查询扩充、检索路由等处理工作，为后续检索和检索后处理做必要的准备，提高检索阶段召回知识的精确度和最终生成的质量。

检索后处理（Post-Retrieval）：在完成检索后对检索出的相关知识块做必要的补充处理，比如对检索结果使用更专业的排序模型与算法进行重排序，或过滤掉一些不符合条件的知识块，留下最需要最合规的知识块在上下文的最前端，协助 LLM 输出高质量内容。

1. RAG 与微调

在提升 LLM 效果的方法中，RAG 和微调是两种主流的方法。下面是这两种方法的比较：
比较内容RAG微调
动态知识更新知识更新时只需动态更新知识库。知识更新时需要重新准备训练数据对模型进行微调，迭代周期长。
训练成本无需额外的训练成本。需要额外的数据准备、标注、清洗成本，以及必要的算力与训练成本。
可解释性可以追溯到具体的数据来源，有较好的可解释性和可追踪性。可解释性较差。

模型能力模型自身不掌握特定知识，需要依赖外部知识库来支持检索和维护数据。模型自身掌握特定知识，对下游应用更友好，在特定任务中使用更简单。

RAG 架构演进

RAG 最早在2020年由 Meta 的技术团队在 Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks 中正式提出，但是在2022年 ChatGPT 出现之前，RAG 并没有获得过多关注。

ChatGPT 的出现使得 RAG 的研究迎来了拐点，大量研究开始关注如何使用 RAG 来提升 LLM 可控性并解决 LLM 在特定领域任务中的幻觉问题，优化 LLM 的推理和生成。

随着 GPT-4、Gemini Pro 等更先进的模型的出现，RAG 在更多任务场景中得以应用，随之而来的是传统 RAG 在实际应用中的问题不断凸显，因此更多的 RAG 范式和优化不断涌现。

+ 1. Naive RAG（朴素RAG）

![](data:image/png;base64...)

朴素 RAG 范式代表了最早的方法论，这一阶段的 RAG 遵循传统的基础流程，包括3个主要的模块与阶段：索引、检索和生成。

朴素RAG面临着诸多的问题：

+ - * 1. 检索召回精度

检索阶段通常会面对精确度和召回率的挑战。如果精确度低，可能导致检索出来的内容带有无关甚至互相矛盾的数据；如果召回率低，可能导致检索出来的数据不够完整，缺失关键信息。

精确度（Precision）：检索结果的 “相关性”

精确度 = （检索到的相关文档数） / （检索到的总文档数）

召回率（Recall）：检索结果的 “完整性”

召回率 = （检索到的相关文档数） / （知识库中所有相关文档总数）

+ - * 1. 大模型自身能力

对于检索出的信息，LLM 是否有能力推理、识别并区分，过滤掉无关或矛盾数据；能否使用检索内容准确生成问题的答案；能否避免在生成内容中包含检索出来的敏感或有害信息，也决定了最终生成结果的质量高低。

+ - * 1. 数据增强的障碍

如何将检索到的信息整合起来生成答案也是一项颇具挑战的任务，有时可能出现生成的内容不连贯、脱节；或者存在多份相似检索内容时生成重复冗余内容的答案；也需要注意要对不同的检索内容的表述方式进行统一，生成风格一致的答案；也需要避免完全照搬检索到的内容，而没有进行信息的整合与处理。

+ - * 1. 上下文大小限制

模型存在上下文大小限制，如果检索出的知识块过多，有可能导致留给生成的 token 过少无法完整生成内容；如果检索出的知识块内容过少，就有可能遗漏一些关键信息，无法让 LLM 完整了解所需知识，导致生成质量下降。因此，如何根据上下文大小确定知识块数量也是需要注意的问题之一。

+ - * 1. 响应性能

与 LLM 直接输出相比，RAG 应用增加了更多处理步骤，并且随着 RAG 的改进优化，未来可能存在更多的步骤，这也意味着端到端的响应性能会下降。如何权衡最终输出质量和响应性能也是一个问题。

+ - * 1. 检索前处理

优化分块策略

常见的分块策略是将文档按固定数量的 token 拆分成块。较大的块能够捕获更多的上下文，但是会产生更多的噪声，并且需要更长的处理时间；较小的块可能无法完整包含所需上下文，导致关键信息被截断。

这促使人们优化递归拆分和滑动窗口方法，通过合并多个检索过程中的全局相关信息来实现分层检索。然而，这些方法仍然无法在语义完整性和上下文长度之间取得平衡。

因此之后又提出了类似 Small2Big 的方法，其中句子（小）用作检索单位，并将前后句子作为（大）上下文提供给 LLM。

元数据索引

可以使用元数据信息（例如页码、文件名、作者、类别时间戳）来丰富数据块。并根据这些元数据过滤检索，从而限制检索范围。

在检索过程中为文档时间戳分配不同的权重可以实现时间感知的检索关联分析，从而确保知识的新鲜度并避免信息过时。

除了从原始文档中提取元数据外，还可以人为构建元数据。例如，添加段落摘要，以及引入假设性问题。这种方法也称为“逆向 HyDE”（Reverse HyDE）：具体来说，利用 LLM 生成文档可以回答的问题，然后在检索过程中计算原始问题与假设问题的相似度，以缩小问题与答案之间的语义差距。

过多的上下文可能包含大量噪声，削弱 LLM 对关键信息的感知。上下文压缩会对检索到的多个文档或片段进行处理，在不丢失重要信息的前提下压缩其长度和数量，来更好地适应模型上下文大小并提高信息质量。压缩方式包括剔除不重要 token、提取关键句、生成段落摘要等方式。

+ 1. Graph RAG

Graph RAG 是一种结构化、分层的 RAG 方法，与使用纯文本片段的朴素语义搜索方法不同，Graph RAG 的过程包括从原始文本中提取知识图谱，构建社区层次结构，为这些社区生成摘要，然后利用这些结构执行 RAG 任务。

基线 RAG 在需要通过遍历不同的信息片段来提供新的综合性见解的时候，难以将信息联系起来。在被要求全面理解大型数据集或单个大型文档中的总结语义概念时，基线 RAG 的表现也不尽如人意。因此，新的 Graph RAG 方法使用 LLM 为数据集创建知识图谱，将该图谱和图机器学习一起使用，在进行复杂信息文档分析时显著提升了问答性能。

Graph RAG 工作的基本流程如下：

+ 1. Agentic RAG
1. Agentic RAG 的特点

传统的 RAG 系统，因其静态的工作流程和有限的适应性，往往难以处理动态的多步骤推理和复杂的现实世界任务。这些局限性促使了 Agentic RAG 的出现。Agentic RAG 通过引入能够进行动态决策和工作流优化的智能体，来处理复杂、实时和多领域的查询，实现了从静态系统到动态系统的范式转变。

Agentic RAG 的主要特点包括：

自主决策：智能体根据查询的复杂性独立评估和管理检索策略。
迭代优化：引入反馈循环以提高检索准确性和响应相关性。
工作流优化：动态协调任务，实现实时应用。

Agentic RAG 目前仍然面临一些问题：

协调复杂性：管理智能体之间的交互需要复杂的协调机制。
计算开销：使用多个智能体增加了复杂工作流程的资源需求。
可扩展性限制：虽然系统具有可扩展性，但其动态特性在高查询量时可能对计算资源造成压力。
- * 1. Agent 组成

一个智能体包括4个组成部分，分别是：

LLM：作为智能体的主要推理引擎，负责解释查询，生成响应，并保持对话的连贯性。
记忆：捕捉跨交互的上下文和相关信息，分为短期记忆和长期记忆。短期记忆跟踪即时对话状态，长期记忆存储积累的知识和经验。
规划：通过反思、查询路由或自我批评，指导智能体的迭代推理过程，确保复杂任务被有效分解和执行。
工具：扩展智能体文本生成之外的能力，使其能够访问外部资源、实时数据或进行专业计算。

事实正确性（Factual Correctness）：生成内容与标准答案的事实重叠。

+ - * 1. 文本清洗

对加载的文本进行清洗。去除 HTML 标签，去除多余的空格。

后续使用的 Chroma 向量数据库，元数据只支持str、int、float、bool类型，因此需要将 metadata 中所有非 Chroma 支持类型的值转为 JSON 格式的字符串。

import re

import json

def clean\_content(documents: list):

    """文本清洗"""

    cleaned\_docs = []

    for doc in documents:

        # 1、page\_content处理：去除多余换行和空格

        text = doc.page\_content

        # 将连续的换行符替换为两个换行符，正则表达式模式：r"\n{2,}"

        # r"" 表示原始字符串（raw string），避免转义字符的特殊处理

        # \n 表示换行符

        # {2,} 是量词，表示前面的字符（换行符）出现 2 次或更多次

        text = re.sub(r"\n{2,}", "\n\n", text)

        text = text.strip()

        # 2、metadata处理：将所有非 Chroma 支持类型的值转为 JSON 格式字符串

        allowed\_types = (str, int, float, bool)

        for key, value in doc.metadata.items():

            if not isinstance(value, allowed\_types):

                try:

                    doc.metadata[key] = json.dumps(value, ensure\_ascii=False)

                except (TypeError, ValueError):

                    # 如果 json.dumps 失败（如包含不可序列化对象），转为 str

                    doc.metadata[key] = str(value)

        # 3、更新文档内容

        doc.page\_content = text

        cleaned\_docs.append(doc)

    return cleaned\_docs

+ 1. 文本分块

加载后的文档往往过长，不适合直接作为 LLM 的上下文。因此在加载文档之后需要对文档内容进行分块，将一个长文档分割成多个块。

如何对文档进行分块，往往决定了检索系统的下限。但是分块方式的选择与具体业务具有很强的关联性，针对不同业务不同文档往往需要定制不同的分块方式。

langchain-text-splitters 中提供了多种文档分块方式，包括：

TokenTextSplitter（使用模型分词器将文本拆分为 token）
SentenceTransformersTokenTextSplitter（使用句子模型分词器将文本拆分为 token）

等。

文本分块时常用的两个参数 chunk\_size 和 chunk\_overlap，分别定义了块的大小和两个块之间重叠部分的大小。

def clean\_content(documents: list):

    """文本清洗"""

    cleaned\_docs = []

    for doc in documents:

        # 1、page\_content处理：去除多余换行和空格

        text = doc.page\_content

        # 将连续的换行符替换为两个换行符，正则表达式模式：r"\n{2,}"

        # r"" 表示原始字符串（raw string），避免转义字符的特殊处理

        # \n 表示换行符

        # {2,} 是量词，表示前面的字符（换行符）出现 2 次或更多次

        text = re.sub(r"\n{2,}", "\n\n", text)

        text = text.strip()

        # 2、metadata处理：将所有非 Chroma 支持类型的值转为 JSON 格式字符串

        allowed\_types = (str, int, float, bool)

        for key, value in doc.metadata.items():

            if not isinstance(value, allowed\_types):

                try:

                    doc.metadata[key] = json.dumps(value, ensure\_ascii=False)

                except (TypeError, ValueError):

                    # 如果 json.dumps 失败（如包含不可序列化对象），转为 str

                    doc.metadata[key] = str(value)

        # 3、更新文档内容

        doc.page\_content = text

        cleaned\_docs.append(doc)

    return cleaned\_docs

1. 指标评估

在进行评估时，我们需要查询文本、回答内容、以及检索到的上下文。

RAG 评估可以采用无参考评估（即不需要预设标准答案）和有参考评估（需要预设标准答案）两种方式。无参考评估通常只需要查询文本、检索上下文、回答内容，而有参考评估除了这些之外还需要标准答案。

这里我们使用 Ragas 库来进行 RAG 系统的评估，对下列指标进行评估：

ContextRelevance 上下文相关性，衡量上下文和问题的相关性。
AnswerRelevancy 答案相关性，衡量生成内容和问题的相关性。
Faithfulness 忠实度，衡量生成内容和上下文的一致性。
ResponseGroundedness 响应真实性，衡量生成内容是否被上下文所支撑。

这些指标都是无参考指标，评估时不需要额外准备用于参考的标准答案。Ragas 会使用LLM 作为评估器来评估各项指标，最终输出每个样本的各项指标分数以及整体平均分数。

def get\_unique\_docs(docs: list[list[Document]]) -> list[Document]:

    """

    文档去重函数

    去除多个文档列表中的重复文档

    Args:

        docs (list[list[Document]]): 多个文档列表

    Returns:

        list[Document]: 去重后的文档列表

    """

    seen = set()  # 用于存储已经遇到的文档内容的哈希值，用于快速检查是否重复

    unique\_docs = []  # 用于存储去重后的文档

    # 遍历所有文档列表

    for sublist in docs:

        for doc in sublist:

            # 将文档内容作为唯一标识符

            # SHA256哈希函数需要字节输入，而不是字符串，所以需要encode

            # hexdigest()：将二进制哈希值转换为十六进制字符串表示，便于存储、比较和显示

            key = sha256(doc.page\_content.encode("utf-8")).hexdigest()

            if key not in seen:

                seen.add(key)

                unique\_docs.append(doc)

    return unique\_docs

HyDE 旨在解决传统 RAG 在检索阶段可能遇到的 “查询 - 文档” 语义鸿沟问题。不直接使用查询去检索，而是使用 LLM 根据查询先生成一个假设性文档，该文档旨在捕捉查询的语义意图，再使用文档去进行检索。通过生成一个更接近理想答案的文档，使检索器能够更好地理解用户意图并检索出相关性更高的文档。

HyDE 是一种零样本方法，不需要专门的标注数据来训练检索器，在查询表述不清晰或检索召回率不足时能发挥巨大作用。

+ 1. 检索后处理：重排序（Rerank）

!图示 中度可信度描述已自动生成

重排序是在检索到文档后，对检索器返回的文档进行二次筛选和重新排序，以选择出少量最相关的文档作为上下文。可以避免信息过载、噪声干扰，并降低计算成本。

+ - * 1. RRF

RRF（Reciprocal Rank Fusion）是一种排名融合算法，用于合并来自多个不同检索器或多种检索方法的排名结果，生成一个统一且更优的最终排名列表的方法。

RRF 的核心思想是：一个文档如果在多个检索方法中都排在靠前的位置，那么它应该在最终的融合排名中获得更高的权重。它的计算方式相对简单且不需要复杂的参数调整。对于每个文档 d，其 RRF 分数计算公式为：

RRF\left(d\right)=\sum\_{r\in R}^{}\frac{1}{k+rank\_{r}\left(d\right)}

d 代表一个文档。
R 代表所有文档列表的集合。
rank\_{r}\left(d\right) 代表文档在检索器排名列表的位次。
k 是一个常数，用于平滑分数。

def reciprocal\_rank\_fusion(

        docs: list[list[Document]], k=60, docs\_return\_num=10

) -> list[Document]:

    """

    倒数排序融合：将多个排序列表融合为一个最终的排序列表，优先考虑在多个列表中排名靠前的文档

    对多查询返回的多个文档列表进行排序，返回一个排序后的文档列表

    """

    # 初始化每个文档的融合分数

    fused\_scores = {}

    # 用于存储去重后的文档，键是内容的哈希值，值是原始的 Document 对象

    unique\_docs\_by\_content = {}

    for doc\_list in docs:

        # 遍历每个有序列表

        for rank, doc in enumerate(doc\_list):

            key = sha256(doc.page\_content.encode("utf-8")).hexdigest()

            unique\_docs\_by\_content[key] = doc

            # RRF实现公式

            fused\_scores[key] = fused\_scores.get(key, 0) + 1 / (rank + k)

    # 按融合分数排序，倒序

    sorted\_content\_hashes = sorted(

        fused\_scores.items(), key=lambda x: x[1], reverse=True

    )

    # 根据排序后的内容哈希值，从 unique\_docs\_by\_content 中取出原始的 Document 对象

    reranked\_docs = []

    for key, \_ in sorted\_content\_hashes:

        reranked\_docs.append(unique\_docs\_by\_content[key])

    return reranked\_docs[:docs\_return\_num]

+ - * 1. 重排序模型

向量数据库的相似度评分（如余弦相似度）本质是向量空间的距离匹配，但无法解决 “语义匹配偏差” 和 “复杂意图理解” 问题。几个问题距离：

问题 1：关键词匹配偏差

例如查询 “苹果手机如何重置”，向量检索可能因 “苹果” 关键词，召回 “苹果种植技术” 的文档（向量特征部分重叠），但二者语义完全无关；反之，查询 “手机恢复出厂设置”，可能因未包含 “重置” 关键词，错过 “苹果手机重置步骤” 的相关文档。

问题 2：无法理解上下文和隐含意图

例如查询 “公司没签合同但发了工资，算雇佣关系吗？”，向量检索依赖 “签合同”“工资”“雇佣关系” 等词的向量匹配，但若知识库中文档表述为 “事实劳动关系认定标准：未签书面合同但存在劳动报酬支付”，二者向量相似度可能不高，导致检索不到；而重排序模型能理解 “没签合同 + 发工资” 与 “事实劳动关系” 的语义等价性。

问题 3：长文本与短查询的匹配失衡

向量嵌入会将长文档压缩为固定维度的向量，可能丢失关键细节（如文档中某一段落才是核心答案）。例如用短查询 “天文台望远镜采购预算” 检索长文档《天文台年度预算表》，向量相似度可能因文档包含 “行政费用、人员薪资” 等其他内容而降低，导致排序靠后。

使用 bge-reranker-base 模型来对检索结果进行重排序。解决了传统向量检索可能存在的 “语义匹配但语义不相关” 问题，通过深度语义理解理解理解进一步优化候选文档的排序。

bge-reranker-base是由北京通用智能研究院（BAAI）开发的轻量级重排序模型，基于 Transformer 架构，专门用于文本对语义相关性评分。其核心能力是：

给定一个查询（query）和一个文档（document），模型会输出一个相关性分数（通常是 0~1 之间的概率），分数值越高表示文档与查询的语义匹配匹配度越高。

相比传统的向量相似度计算（如余弦相似度），它的优势在于：

能捕捉更细微的语义关联（如同义词、上下文语境、隐含意图）；
对长文本的理解更准确，不受限于向量嵌入的固定维度限制；
轻量级（base 版本参数较小），适合在资源有限的场景部署。

向量数据库的相似度排序：负责“效率优先”的召回，从海量数据中快速筛选出 “可能相关” 的候选集（如 Top 50），解决 “查得快” 的问题；

重排序：负责“精度优先”的筛选，在候选集中精准找出 “真正相关” 的文档（如 Top 10），解决 “查得准” 的问题。

没有重排序，向量检索的结果可能存在大量 “无效关联”；没有向量检索，重排序则需面对海量数据，失去效率优势。二者结合，才能实现 RAG 检索 “又快又准” 的目标。

def reciprocal\_rank\_fusion(

    docs: list[list[Document]], k=60, docs\_return\_num=10

) -> list[Document]:

    """

    倒数排序融合：将多个排序列表融合为一个最终的排序列表，优先考虑在多个列表中排名靠前的文档

    对多查询返回的多个文档列表进行排序，返回一个排序后的文档列表

    """

    # 初始化每个文档的融合分数

    fused\_scores = {}

    # 用于存储去重后的文档，键是内容的哈希值，值是原始的 Document 对象

    unique\_docs\_by\_content = {}

    for doc\_list in docs:

        # 遍历每个有序列表

        for rank, doc in enumerate(doc\_list):

            key = sha256(doc.page\_content.encode("utf-8")).hexdigest()

            unique\_docs\_by\_content[key] = doc

            fused\_scores[key] = fused\_scores.get(key, 0) + 1 / (rank + k)

    # 按融合分数排序

    sorted\_content\_hashes = sorted(

        fused\_scores.items(), key=lambda x: x[1], reverse=True

    )

    # 根据排序后的内容哈希值，从 unique\_docs\_by\_content 中取出原始的 Document 对象

    reranked\_docs = []

    for key, \_ in sorted\_content\_hashes:

        reranked\_docs.append(unique\_docs\_by\_content[key])

    return reranked\_docs[:docs\_return\_num]

class RetrievalCache:

    """检索结果缓存"""

    def \_\_init\_\_(

            self,

            embedding\_dim: int,

            max\_cache\_entries: int = 512,

            similarity\_threshold: float = 0.9,

            ttl: int = 3600,

    ):

        self.max\_cache\_entries = max\_cache\_entries  # 最大缓存条目数

        self.similarity\_threshold = similarity\_threshold  # 相似度阈值

        self.ttl = ttl  # 老化时间

        # 缓存字典 {faiss\_index\_id : {'docs': [Document], 'timestamp': datetime}}

        self.cache: OrderedDict[int, dict[str, any]] = OrderedDict()

        # 创建 FAISS 索引，存储查询嵌入向量

        self.query\_vectorstore = faiss.IndexFlatL2(embedding\_dim)

        # 用于 FAISS 索引的内部 ID， ID 通常是添加的顺序

        self.current\_index\_id = 0

    def \_\_call\_\_(self, func):

        @functools.wraps(func)

        def wrapper(embedding: list[float], k: int = 20) -> list[Document]:

            # 将嵌入向量转换为 numpy 数组

            query\_embedding\_np = np.array(embedding).astype(np.float32)

            # 惰性清理

            self.\_lazy\_evict()

            # 如果缓存不为0，则在 FAISS 中查找相似的查询嵌入

            if self.query\_vectorstore.ntotal > 0:

                # 搜索最相似的 1 个向量

                distances, indices = self.query\_vectorstore.search(

                    query\_embedding\_np.reshape(1, -1), 1

                )

                # 得到该向量与查询向量的 L2 距离的平方，以及对应的 ID

                distance = distances[0, 0]

                cached\_id = indices[0, 0]

                # 我们认定如果 l2\_distance <= (1 - similarity\_threshold)^2 则足够相似

                if (

                        cached\_id != -1

                        and distance <= (1 - self.similarity\_threshold) \\ 2

                        and cached\_id in self.cache

                ):

                    # 将命中的项移动到队尾

                    self.cache.move\_to\_end(cached\_id)

                    # 更新被命中的缓存的时间戳

                    self.cache[cached\_id]["timestamp"] = datetime.now()

                    # 返回命中的结果

                    return self.cache[cached\_id]["docs"]

            # 如果未命中缓存，执行检索，并将结果存入缓存

            retrieved\_docs = func(embedding, k)

            self.\_add\_to\_cache(query\_embedding\_np, retrieved\_docs)

            return retrieved\_docs

        return wrapper

    def \_add\_to\_cache(

            self, query\_embedding: np.ndarray, retrieved\_docs: list[Document]

    ):

        """将查询嵌入和检索结果添加到缓存"""

        self.\_lazy\_evict()

        # 将新的嵌入添加到 FAISS

        self.query\_vectorstore.add(query\_embedding.reshape(1, -1))

        # 缓存检索结果

        self.cache[self.current\_index\_id] = {

            "docs": retrieved\_docs,

            "timestamp": datetime.now(),

        }

        self.current\_index\_id += 1

    def \_lazy\_evict(self):

        """惰性清理"""

        curremt\_time = datetime.now()

        removed\_entries = []

        # 清理过期数据

        for faiss\_index\_id, entry in list(self.cache.items()):

            if (curremt\_time - entry["timestamp"]).total\_seconds() < self.ttl:

                break

            del self.cache[faiss\_index\_id]

            removed\_entries.append(faiss\_index\_id)

        # 清理超出容量的数据

        while len(self.cache) > self.max\_cache\_entries:

            removed\_entries.append(self.cache.popitem(last=False))

        # 从 FAISS 中清理数据

        if removed\_entries:

            self.query\_vectorstore.remove\_ids(

                np.array(removed\_entries).astype(np.int64)

            )

    def clear(self):

        """清空缓存"""

        self.cache.clear()

        # 重新初始化 FAISS 索引

        self.query\_vectorstore = faiss.IndexFlatL2(self.query\_vectorstore.d)

        self.current\_index\_id = 0

生成结果缓存的 Key 通常是查询文本+检索到的文档 ID 列表，Value 是 LLM 生成的回答。

这种缓存仅适用于无上下文的独立查询、高频且固定的问答对等场景。如果在生成时需要格外考虑其他信息，这种缓存可能并不适用。

某些场景下 LLM 生成结果时会综合多中信息，包括当前查询文本、检索到的相关文档和知识、对话历史、用户画像、时间地点等。因此当上述某些信息发生变化时，即使查询文本完全相同，也可能需要生成不同的回答。在这种场景下，需要设置更加精细化的缓存。

这种情况下如果想要构建有效的生成结果缓存，就需要在缓存的 Key 中纳入更多的信息，比如将 Key 设置为整个对话历史、或者对话历史中关键特征、亦或是使用所有信息的语义缓存并在查找时计算相似度是否达到阈值。

Graph RAG
传统 RAG 的局限

传统的基于平面文本检索RAG 系统虽然在一定程度上缓解了 LLM 知识之后和幻觉问题，但在应对复杂场景下仍面临着诸多挑战：

+ - * 1. 专业领域的复杂查询理解

专业领域的查询通常涉及复杂的术语、行业特定行话以及高度抽象的概念，需要精确的解释和多步骤的推理。传统的 RAG 方法主要依赖关键字匹配和向量相似度检索，这不足以准确和全面地捕捉所需的深层语义间的细微差别和多步骤推理过程。

例如，当查询概念 A 和 概念 D 直间的联系时，传统 RAG 系统通常检索与 A 和 D 直接相关的信息，而可能忽略了 B 和 C 这样的中间概念或隐含路径，这种狭隘的检索范围限制了 RAG 的广泛情景理解和复杂推理能力，导致无法将这些概念联系起来构建出完整的逻辑链条来回答复杂问题。结果是系统可能提供表面上相关但缺乏深度洞察的答案，无法满足专业用户对复杂知识推理的需求。

+ - * 1. 不同数据源的知识整合

领域知识通常来自不同的数据源，例如教材、论文、行业报告、技术手册等，这些文档的质量、准确性和完整程度都有差异。更重要的是，从多个文档中检索到的知识通常是扁平的、离散的文本片段，它们之间缺乏明确的层次关系和语义链接。

这种碎片化的知识表示阻碍了在相关知识点之间建立牢固联系的能力，导致对复杂概念的理解碎片化，并降低了利用领域特定专业知识的效率。模型难以从这些孤立的片段中构建出连贯、结构化的知识图谱，从而限制了其进行跨文档、多维度知识综合和推理的能力。此外，信息冗余和矛盾也可能在不同数据源的集成中出现，进一步影响检索质量和生成答案的准确性。

+ - * 1. 大规模系统的效率瓶颈

随着知识库规模的不断扩大，传统 RAG 系统面临显著的效率瓶颈。外部知识库包含大量与领域无关的信息，而领域特定术语和关键信息总是零星分布在这些海量文档中。

这导致检索过程需要扫描大量的无关内容，不仅增加了计算开销和检索延迟，还可能因为“信息过载”而导致检索结果的噪声。在查询编码和相似度计算阶段，对大规模向量数据库的频繁访问也可能成为性能瓶颈。同时，缺乏对文档结构和内容重要性的精细化理解，使得系统难以优先处理最有价值的知识，从而进一步加剧了效率问题，影响了用户体验，尤其是在需要实时响应的应用场景中。

+ - * 1. 意义构建能力的缺失

传统 RAG 方法在处理需要全局理解整个数据集的查询时，明显暴露出其意义构建能力的缺失。例如“过去十年中，交叉学科研究对科学发现的关键影响趋势是什么？”这类查询并非简单地寻找特定事实或局部信息，而是要求系统能够理解“人与人、地点与事件之间的联系，以预测其发展轨迹并有效行动”。

然而，传统的 RAG 方法本质上是局部化的，它将整个语料库分解为离散的、独立的文本块进行向量化和检索。这种“平面化”的处理方式，使得系统难以捕捉到散布在不同文档块之间、隐含的复杂关系和高阶关联。它无法支持对整个语料库进行全局性的意义建构，例如发现跨越多个文档的演变趋势、推断实体间的间接联系，或是从碎片化信息中综合出更深层次的见解。这意味着，尽管 LLM 本身具备意义建构的潜力，但向量 RAG 的检索机制却无法为其提供足够结构化、关联性的上下文，从而限制了 LLM 在复杂、需要宏观洞察的意义建构任务中的表现。

1. Graph RAG 介绍

为了应对这些局限，基于图的检索增强生成（Graph RAG）应运而生。

Graph RAG 巧妙地利用图结构来组织和检索知识，这赋予了它独特的优势。它能以两种主要方式运用图：

+ - * 1. 基于索引的 Graph RAG

这种范式下，图的主要作用是作为一个高级的索引层，用于组织原始的文本块。它不是一个传统的、严格的“知识图谱”，而是文本块之间的关系图。

图中每个节点代表一个原始的文本块，边表示这些文本块之间与查询相关的关系，这样更容易地“定位”相关的知识。当用户提出查询时，系统可以在这个“索引图”上进行导航，快速找到所有相关的文本块，即使它们在原始文档中是分散的。

+ - * 1. 基于知识的 Graph RAG

这种范式下，图本身就是承载实际“知识”的主体。它是一个传统的知识图谱，其中存储的是高度结构化、抽象化的事实和关系。这个图可能是从语料库构建出来的，也可能是直接使用已有的知识图谱。

通过建模节点（实体）之间的依赖关系，Graph RAG 不仅能识别出围绕特定主题或实体的相关知识片段，还能确保全面且深入的知识检索。更进一步，Graph RAG 还支持通过导航节点间的相关链路进行高效搜索，这使得它能够进行多跳推理，回答那些需要跨越多个信息点才能得出结论的复杂问题。

+ 1. 切分文本块

语料库中的文档被分割为文本块，LLM 从每个块中提取信息以供下游处理。块的大小是一个需要设计的参数，较长的文本块能够减少 LLM 的调用次数，降低成本，但是也会减低文本块中信息的召回率。

+ 1. 抽取实体与关系

LLM 根据提示词从给定的块中提取实体和关系，并为实体和关系生成简短描述。

例如，文本块如下：

李白，字太白，号青莲居士，又号谪仙人，是中国唐代伟大的浪漫主义诗人，被后世誉为’诗仙’。他与杜甫并称为’李杜’，是中国文学史上两颗璀璨的巨星。李白一生漫游，创作了大量气势磅礴、想象丰富的诗歌。他曾被唐玄宗召入宫中，但不久后便离开了朝廷。

从上文中提取出实体和关系：

实体：李白

描述：李白是中国唐代著名的浪漫主义诗人，被誉为’诗仙’。

实体：杜甫

描述：杜甫是中国唐代另一位伟大诗人，与李白并称’李杜’。

实体：唐代

描述：唐代是中国历史上的一个重要朝代，李白和杜甫都生活在这一时期。

实体：唐玄宗

描述：唐玄宗是唐朝的一位皇帝，曾召李白入宫。

关系：李白 和 杜甫 之间的关系

描述：李白与杜甫并称为’李杜’，是中国文学史上的两位杰出诗人。

关系：李白 和 唐代 之间的关系

描述：李白生活在中国唐代，是唐代诗人。

关系：李白 和 唐玄宗 之间的关系

描述：唐玄宗曾召李白入宫。

对于通用领域，默认的提示词可能提取通用的命名实体（如人、地点、组织等）。而对于某些特定领域，为了提高提取的准确率和适用性，可以通过在 LLM 的提示词中添加少样本示例，来帮助 LLM 在特定领域更好地识别实体和关系。

除了抽取实体和关系之外，LLM 还可以根据提示词提取实体的声明（claims）。声明是关于实体的重要事实描述，例如日期、事件以及与其他实体的互动等。

例如从上面文本中提取声明：

李白的字是’太白’，号’青莲居士’，又号’谪仙人’。

李白被后世誉为’诗仙’。

李白与杜甫并称为’李杜’。

李白曾被唐玄宗召入宫中。

李白在被唐玄宗召入宫中后不久便离开了朝廷。

与实体和关系抽取类似，声明抽取也可以通过少样本学习提供特定领域的指导，以确保抽取出的声明符合该领域的特点和需求。

LLM 倾向于从较大的块中提取较少的实体，在一个样本数据集上实践发现当块大小为 600 token 时，GPT-4 提取的实体引用几乎是块大小为 2400 token 时的两倍。为了解决这个问题，采用了一种自我反思（Self-Reflection）的提示工程方法，在一次提取之后使用 LLM来评估是否所有实体都被提取出来。如有遗漏，将提取的实体反馈给 LLM，并提示它继续搜集可能遗漏的任何实体。

+ 1. 构建知识图谱

提取实体、关系、声明的过程中可能会创建单个元素的多个实例，因为一个元素通常会在多个文档中被多次提及和提取。实体和关系的实例会组成图的节点和边。实体对应的所有描述会被总结汇总到节点和边上。关系也会被汇总，某个关系的重复数量会作为边的权重。声明也会以类似的方式汇总到相应的实体和边上。

提取出来的实体可能会存在“同名不同物”的情况，也就是对应现实世界同一事物的实体具有多个不同的名字。对于这种情况可以通过调整提示词或编写代码的方式来进行匹配。此外，Graph RAG 本身对重复实体也具有鲁棒性，因为重复实体通常会在后续步骤中聚类成簇，并进行统一的总结。

+ 1. 构建图社区

利用社区检测算法将图划分为一个个强连通节点组成的社区。比如分层使用 Leiden 社区检测算法（让每个社区内部的连接尽可能多，社区间的连接尽可能少），先找出最明显的大社区，再递归地在大社区中划分子社区，直到某个社区内部无法在划分出更小的、强连接的子社区，就到达了叶社区。

这样一来，每层都提供了一个独特的社区划分，确保图中所有节点都属于某个社区，且每个节点只属于一个社区（互斥且集体穷尽），使得我们可以从不同的粒度来理解图谱。高层次的社区可以看到整个图谱的宏观结构，低层次的社区可以深入了解内部详细信息。当 LLM 回答时可以定位到与查询相关的某些社区，更快更准确地获取所需信息。

+ 1. 生成社区摘要

使用一种可扩展到庞大数据集的方式，来为社区层次结构中每个社区生成摘要报告。这些摘要可独立地用来理解数据集的全局结构和语义；同时也会作为图谱索引的一部分，用于回答全局查询；即使不用于查询，这些摘要也可以用来快速理解语料库，比如用户可以通过高层次的社区摘要寻找感兴趣的主题，然后翻阅低层次的摘要去寻找该主题下的子主题的更多信息。

Graph RAG 生成摘要的方式是将各种元素的摘要（包括节点、边、声明相关的摘要）填充到预设的社区摘要模板之中来生成社区摘要，低层次的摘要用于生成高层次的摘要。具体过程如下：

叶社区：先从叶社区中优先选择最重要的元素摘要，迭代添加到 LLM 的上下文窗口中，直到达到 LLM 的 token 限制。在确定优先级时，会遍历图中所有的边，根据边的源节点和目标节点的总度数来降序排列这些边，之后按照优先依次将边的源节点的描述、目标节点的描述、边的描述、与节点和边相关的声明添加到 LLM 的上下文之中。

高层次社区：如果一个高层级社区中所有元素摘要（包含其子社区的摘要）加起来没有超过 LLM 的 token 限制，则按照叶社区的方式处理，并总结社区内所有元素的摘要；否则根据子社区的摘要的 token 数量对子社区降序排名，并迭代地使用子社区的摘要（较短）来替换该子社区关联的元素摘要（较长），直到所有信息都能放入 LLM 的上下文窗口中。

这个社区摘要的生成是 Graph RAG 实现“从局部到全局”理解和回答的关键。通过这种分层、优先级化的摘要，Graph RAG 能够高效利用 LLM 的上下文窗口处理超大规模的数据集，生成多粒度的摘要，为全局查询提供结构化、高相关的背景信息。这使得 LLM 不再需要阅读和理解海量原始文本，而是可以直接通过这些提炼好的，有层次的社区摘要来获取信息，提高了效率和准确性。

+ 1. 全局查询

知识图谱被分为不同层次的社区，从非常具体（叶社区）到非常宏观（顶层社区）都有摘要报告，这就引出一个问题：面对用户关于全局的查询，哪个层次的社区摘要能提供最佳的“细节”和“范围”的平衡？如果选择的层次过低，可能会有太多零碎细节，LLM 难以综合；如果选择的层次太高，可能会丢失重要的细节信息。

Graph RAG 对查询进行分析，以确定它需要的是宽泛的高层次的响应，还是更加具体详细的回答。如果高层的的摘要足以回答问题，LLM 就会直接使用它，否则就会深入到更细粒度的子社区摘要，或者社区中的原始文本块与实体信息。

一旦确定了使用哪个层次的社区摘要，生成全局答案的过程如下：

准备社区摘要：随机打乱指定层次的所有社区摘要，并将社区摘要分割成预设大小的块，确保相关信息均匀分布在不同块中而不是集中在单个上下文窗口中，避免因为 LLM 的 token 限制而截断大量相关信息。

映射社区答案：对于每个社区摘要块使用 LLM 并行生成中间答案，同时生成一个 0~100 的分数表示该答案对回答用户查询的帮助程度，并过滤掉 0 分的答案，确保只有对最终回答有帮助的答案才进入下一步。

归约全局答案：按分数降序排序中间答案，迭代地将中间答案添加进新的上下文窗口中直到达到 token 限制，LLM 根据该上下文生成最终答案。

这种分而治之再合而为一的策略，使得 Graph RAG 能够处理大规模知识库的复杂查询，并生成准确全面的回答。

+ 1. 局部查询

Graph RAG 除了能够处理需要综合整个知识库的宏观全局查询外，也擅长回答关于特定实体或概念的局部查询。这类查询通常涉及对某个具体对象或其直接相关信息的深入理解。如“洋甘菊有哪些治愈功效？”。

Graph RAG 的局部查询模式旨在提供最佳的“特异性”和“相关性”的平衡。与全局查询不同，局部查询无需考虑社区层级的选择，因为它的目标是聚焦于与查询实体最直接相关的信息。

在进行局部查询时，系统首先从知识图谱中识别与用户输入语义相关的实体集，将这些实体作为知识图谱的入口，以这些实体为中心获取邻接实体、关系、相关声明、社区摘要，将获取到的元素按优先级排序后输入 LLM 的上下文窗口，直到达到 token 限制，LLM 根据上下文生成回答。

这种针对性强、结合结构化与非结构化信息进行检索的策略，使得 Graph RAG 在处理关于特定对象或概念的细粒度查询时，能够提供准确、详细且上下文丰富的回答。

1. 基于已有知识图谱的 Graph RAG

基于已有知识图谱时搭建 Graph RAG 时，我们就需要专注于如何将用户的自然语言查询有效地转换为对图谱的检索，并利用检索结果增强 LLM 的生成。

对于已有的知识图谱，我们仍需要做一些准备工作。首选需要检查知识图谱中数据的质量和完整性，确定图中实体和关系是否准确无误、是否包含足够的信息属性、是否能表达足够细致的语义以支持复杂查询；其次，如果知识图谱原本是结构化的，但是我们希望也能利用相关的非结构化信息（如文档、报告、摘要），我们可以将非结构化信息存储在图谱中并通过关系与实体连接；之后，我们需要为图谱中的所有文本内容生成嵌入向量，并建立向量索引用于后续的语义检索。

对于用户查询，可以同时或按顺序使用多种方式对知识图谱进行检索：

基于语义相似度检索：使用关键词检索或向量相似度搜索匹配相关的节点。

基于逻辑规则的检索：识别实体、关系和意图，并匹配规则进行检索。

LLM 生成查询语句：使用 LLM 将用户查询直接转换为查询语句进行查询。

基于强化学习的检索：将检索过程看作一个序列决策问题，让智能体通过试错来学习如何在知识图谱中导航和遍历，来寻找相关信息。

分块（Chunking）是 RAG 从"玩具"走向"工业级"的分水岭。检索不准 80% 不是模型问题，而是文档"切碎了"或"切错了"。

四种切片策略对比

策略复杂度优点缺点适用场景
递归字符分块低通用、保留语义边界仍有概率切断逻辑通用场景首选

1. 递归字符分块（Recursive Character Splitting）

最重要的通用方案，LangChain 默认推荐。

核心逻辑：不是按长度一刀切，而是"带着备选方案的尝试切分"。

分隔符优先级：\n\n（段落）→ \n（行）→ （词）→ ""（字符）

关键参数：

chunk_size：通常 512-1024 token
chunk_overlap：50-100 字符，给断开的语义贴"创可贴"

6. 文档块摘要索引（Chunk Summary Index）

先让 LLM 把每个块总结成摘要，用摘要向量索引，检索时匹配摘要定位原文。

重排序与融合

来源: 知识星球/AI基础的概念/2.3RAG检索后阶段（Post-Retrieval）/ 整理时间: 2026-05-30

核心概念

向量检索是"海选"，检索后处理是"决赛圈精挑细选"。两个核心技术：Rerank（重排序）和 RRF（互惠排名融合）。

Rerank（重排序）

让昂贵的 Cross-Encoder 深度模型对初筛结果进行精排。

为什么需要 Rerank

向量检索擅长模糊匹配，但对精确数字、否定词经常翻车
Bi-Encoder（Embedding 模型）速度快但精度有限
Cross-Encoder 精度高但计算量 O(N)，只能用于精排

典型流程

向量检索 Top-50 → Rerank 精排 → Top-5 送给 LLM

BGE-Reranker 使用

RRF（互惠排名融合）

一种不看"得分高低"，只看"排名先后"的公平投票机制。

核心公式

score(d) = \sum_{r \in R} \frac{1}{k + r(d)}

r(d)：文档在排行榜里的排名
k：平滑因子（通常 60），防止第一名权重过大

为什么不用加权评分

方案特点
加权评分Score = 0.3×Vector + 0.7×Keyword，需要手动调参，数据一变权重失效
RRF无需调参，只需排名，鲁棒性极强

RAG 评估与优化

来源: 知识星球/AI基础的概念/2.4RAG生成阶段 & 2.5RAG总体/ 整理时间: 2026-05-30

核心概念

"没有评估，就没有优化。"RAG 评估基于 RAGAS 框架的四个核心指标，分别测量检索和生成两个环节的质量。

RAG 四大评估指标

检索质量

指标问题衡量对象
Context Recall找全了吗？检索片段是否覆盖答案所需的全部知识点
Context Precision找准了吗？有用信息是否排在前面，噪音多不多

生成质量

指标问题衡量对象
Faithfulness瞎编了吗？答案是否完全来自检索片段（反幻觉）
Answer Relevance答非所问吗？答案是否直击用户问题核心

对症下药

Context Recall 低 → 优化 Embedding 和分块策略
Context Precision 低 → 加 Reranker 重排
Faithfulness 低 → 调低 Temperature，加 Prompt 约束
Answer Relevance 低 → 优化 Prompt 模板

Self-RAG

传统 RAG 是死板流水线，Self-RAG 通过植入反思令牌实现闭环反馈：

[Retrieve]：按需检索，知识储备不足时才翻书
[IsRel]：相关性过滤，不相关的直接踢掉
[IsSup]：忠实度检查，每句话对比原文
用户提问 → 意图识别 → {需要检索?} → Yes → 多路检索+Rerank
                                 → No → 模型原生知识
         → [IsRel] 过滤 → 生成答案 → [IsSup] 自检
         → 忠实度低 → 自我修正 → 忠实度高 → 输出

注意：真正的 Self-RAG 靠微调，Prompt 里写"请反思"只是伪 Self-RAG。

Q: 为什么不用 GraphRAG？

A: 知识是文档型和 QA 型，客服场景需要的是材料内内容问答，不需要高层级信息总结。GraphRAG 构建成本高、知识难更新。

Q: 如何做百万级数据的向量化？

A: 推荐购置云端向量数据库（如 Milvus Cloud），多节点高 CPU/内存共同负载。

Q: 混合检索为什么有效？

A: 稀疏检索精确匹配关键词/术语，稠密检索理解语义解决同义词问题，两者互补。

Q: Rerank 如何实现？

A: 使用 BGE-Reranker 对召回文本做基于 Cross-Encoder 的相似度排序，或加权计算重要性得分。
